Harness Engineering：驾驭工程介绍

发表于 2026-07-17 更新于 2026-09-08 分类于 Harness Engineering
Harness Engineering 学习笔记：概念边界、治理维度、发展脉络与八类常见失效模式。

Harness Engineering（本文译作“驾驭工程”）是 2025—2026 年间在 Agent 工程讨论中快速流行的术语。它还不是一套由标准组织定义、边界完全统一的学科，更适合被理解为一组围绕智能体运行时的工程实践：通过工具、状态、上下文、权限、验证、预算和可观测性，让模型更可靠地执行真实任务。

本文先建立概念边界，再通过一个故意保留缺陷的 Naive Agent，观察缺少 Harness 时会出现什么问题。下一篇文章再逐一实现对应机制。

一个便于理解的教学类比

Harness 原意可以指用于控制和连接的挽具、马具或安全带。将它放进 Agent 系统，可以做一个简化类比：

  • 模型（Model）：提供语言理解、推理和生成能力；
  • 驾驭系统（Harness）：提供工具、反馈、权限和运行约束；
  • 执行环境（Environment）：代码仓库、浏览器、数据库、操作系统和外部服务；
  • 工程师或用户：定义目标、验收标准和风险边界。

Model 决定系统可能具备哪些能力；Harness 决定这些能力如何被调用、约束、观察和验证；Environment 则决定 Agent 实际能接触和改变什么。最终结果由三者与任务共同决定，Harness 不能保证固定的能力下限，错误的 Harness 也可能降低模型表现。

组成部分 类比 核心作用 关键描述
Model 引擎 决定 Agent 的能力上限 生成、推理、代码理解等核心能力都在模型权重里，但 “引擎再强，没有底盘和刹车，跑不过 100 公里就失败”
Harness 底盘 + 刹车 + 方向盘 保住 Agent 的运行下限，让上限真正落地 包含循环刹车、状态持久化、工具编排、上下文管理、验证闭环，是让模型能稳定持续运行的工程系统

Harness 主要负责什么

一个面向真实任务的 Harness 通常需要覆盖以下责任。具体产品不一定使用相同名称，也不一定把它们实现为独立模块。

责任 作用
Runtime Control 管理循环、最大轮数、超时、取消和终止状态
Tool Contract 定义工具名称、参数 Schema、结果结构和错误分类
Context Management 选择、压缩和按需加载模型当前需要的信息
Task State & Memory 保存任务清单、检查点、项目约定和可恢复状态
Permission & Sandbox 限制文件、命令、网络、密钥和高风险动作
Verification 使用测试、类型检查、浏览器和其他外部证据验证结果
Budget 限制 Token、调用次数、执行时间和费用
Observability 记录 Trace、日志、指标、失败原因和人工干预

Tools、Hooks、Skills、Memory 文件和 Subagents 都可以是实现这些责任的手段，但它们不是 Harness 的唯一实现方式。

四种常见运行形态

下面比较的是应用和执行环境，不是对某个模型品牌的永久能力说明。

运行形态 可见信息 可执行能力 典型约束
纯聊天应用 当前对话和用户提供的内容 主要生成文本 依赖用户手动执行建议
带托管工具的 Agent 应用 对话、上传文件、连接器数据 浏览、代码执行、数据分析等托管工具 受产品授权和远程沙箱限制
工作区编码 Agent 授权仓库、终端输出、Git 状态 修改文件、运行测试和构建工具 受工作区权限和本地环境限制
生产级自主 Agent 业务状态、外部服务和持久任务记录 跨系统执行长任务 必须强化权限、幂等、预算、审计和人工审批

真正需要比较的，不只是底层模型，还包括模型能看到什么、能调用什么、发生错误后能否恢复，以及系统如何验证最终结果。

为什么 Harness 会显著影响 Agent 表现

模型能力经常表现出不稳定和任务相关的波动：同一个模型可能在一条轨迹上正确完成复杂修改，也可能在另一条轨迹上漏读关键文件、重复调用工具或过早宣布完成。

Harness 的作用不是把弱模型变成万能模型，而是通过下面几类工程手段减少不必要的失败：

  • 在动作前提供更相关的信息和明确边界；
  • 给模型配置更容易正确使用的工具；
  • 在动作后提供可解释的反馈；
  • 让失败能够重试、恢复或升级给人类；
  • 使用固定任务集和 Trace 验证 Harness 修改是否真的有效。

两个公开案例

案例 公开结果 应如何解读
Improving DeepAgents with Harness Engineering（LangChain，2026-02-17） 在其 Terminal-Bench 2.0 实验中，保持 GPT-5.2-Codex 不变，调整 Harness 后通过率从 52.8% 提升到 66.5%，增加 13.7 个百分点 说明 Harness 可以作为独立工程变量进行实验；结果不能直接外推到所有模型和任务

排行榜名次、模型版本和产品能力都会变化，因此引用公开结果时应同时保留发布日期、模型、任务集和评测条件。

Prompt、Context 与 Harness：三个相互重叠的关注面

Prompt Engineering、Context Engineering 和 Harness Engineering 不是严格的三代技术，也不是谁完全取代谁。它们描述的是三个相互协作、边界有重叠的工程关注面。

关注面 核心问题 常见内容
Prompt Engineering 如何清晰表达目标、约束和输出格式 System Prompt、示例、格式要求、行为规则
Context Engineering 当前这次调用应该让模型看到什么 对话历史、代码、检索结果、工具输出、摘要和缓存前缀
Harness Engineering 如何管理一个持续观察、行动和反馈的系统 循环、工具、状态、权限、验证、预算和可观测性

同一项设计可能同时落入多个关注面。例如 Tool Schema 是模型输入的一部分，因此属于 Context；它也定义了模型如何行动，因此又是 Harness 的工具契约。

更稳妥的结论是：

  • Prompt 负责表达；
  • Context 负责选择和组织当前可见信息；
  • Harness 负责运行时的行动、反馈和治理。

它们通常同时存在，而不是按版本依次淘汰。

从控制视角理解 Harness

MartinFowler.com 的 Harness engineering for coding agent users 提供了一个很实用的二维视角。

动作前与动作后

  • Feedforward Control：在 Agent 动作之前提供目标、约束和允许范围；
  • Feedback Sensor：动作之后观察结果，并提供下一轮纠偏信号。

确定性与推断式

  • Computational：由程序确定执行，例如权限检查、测试、类型检查；
  • Inferential：需要模型或人类进行语义判断，例如代码评审和视觉质量评价。
动作前：Feedforward 动作后：Feedback
确定性控制 Tool Schema、路径白名单、命令 Allowlist、预算 pytest、类型检查、Lint、浏览器断言
推断式控制 AGENTS.md、Skills、示例和任务说明 LLM Review、视觉评估、人工评审

可靠系统通常优先使用确定性控制；只有难以形式化的质量标准，才主要依赖推断式评估。

Agent、Scaffolding、Framework、Runtime 与 Harness

这些术语没有统一的标准边界，下面只给出本文使用的工作定义。

术语 本文工作定义 与 Harness 的关系
Agent 能够观察环境、选择动作并使用工具推进目标的软件实体 Agent 是运行主体，Harness 是管理其运行的外围系统
Scaffolding 模型调用周围的提示、工具或执行脚手架 有时指 Context 装配，有时范围接近 Harness，必须结合来源判断
Framework 帮助开发者构建 Agent 的类库和抽象 可以提供 Harness 的积木，也可能直接附带高层 Harness
Runtime 执行状态、调度、持久化和中断等逻辑的运行层 通常是 Harness 的重要基础，但不能自动代替权限和验收策略
Harness 将模型连接到环境，并负责工具、状态、控制、反馈和治理的系统 可以由 Framework、Runtime 和业务代码共同组成

判断一个系统是不是“成熟 Harness”，不要只看它有没有 Prompt 模板或 Agent Loop，而要继续检查：

  • 循环能否可靠退出；
  • 工具错误能否被机器识别；
  • 任务中断后能否恢复；
  • 高风险动作是否受权限控制；
  • 完成状态是否有外部证据；
  • Token、时间和费用是否有上限；
  • 失败后能否通过 Trace 解释原因。

八类代表性失效模式

这八类是本文用于教学的检查清单，不是行业标准或完整故障分类。

# 失效模式 代码中的表现 更准确的后果
1 循环失控 业务循环使用 while True，没有任务级停止协议 模型可能重复动作；没有外部保护时会持续调用 API
2 Context 溢出 每轮重新发送不断增长的完整历史 单轮输入持续增长，累计输入 Token 可能接近二次增长
3 Cache Miss 每轮修改 System Prompt 前缀 降低可复用前缀的缓存命中量；影响大小取决于厂商和命中 Token 数
4 Tool 错误不可见 异常对模型返回空字符串，pytest 丢失返回码 Agent 无法可靠区分空结果、参数错误、权限错误和执行失败
5 任务状态丢失 不保存当前任务、证据和下一步动作 内存状态丢失，但磁盘副作用可能保留，留下难以解释的半成品
6 缺权限闸 read_file、write_file 没有工作区边界 可能读取敏感文件或覆盖进程权限范围内的任意可写文件
7 缺自动化验证 没有 Tool Call 就直接退出 模型可能错误地提前宣布完成，且没有外部证据纠正
8 成本失控 没有 Token、费用、时间和 Tool Call 预算 长任务、重试或 Subagent 并发可能持续消耗资源

真实系统还需要考虑更多问题：

  • API 超时、限流和网络故障；
  • Tool Output 中的 Prompt Injection；
  • 密钥和敏感数据泄漏；
  • 有副作用操作的幂等性；
  • 多 Agent 并发写入冲突；
  • Checkpoint 损坏；
  • 验证器错误和测试过拟合；
  • 模型升级后旧 Harness 规则失效。

八类应对机制

下一篇文章将使用下面八个机制治理上述故障：

# 机制 主要解决的问题
1 Runtime Control 最大轮数、超时、取消和明确终止状态
2 Tool Contract Schema、结构化错误、调用关联和超时
3 Checkpoint & Task Ledger 任务拆解、持久状态、证据和断点恢复
4 Context & Cache Management Token 预算、上下文压缩和稳定缓存前缀
5 Permission & Sandbox 路径、命令、网络、密钥和人工审批
6 Verification & Evaluation 确定性测试优先，推断式评估作为补充
7 Subagent Isolation 独立 Context、受限工具和结构化结果
8 Budget & Observability Token、调用次数、时间、费用、Trace 和告警

这些机制不是严格的一一对应关系。例如 Runtime Control 可以缓解成本风险，但不能代替费用预算；Subagent 可以隔离主 Context，却可能增加系统总成本。

LangChain 的三层产品示例

LangChain 创始人 Harrison Chase 在 Agent Frameworks, Runtimes, and Harnesses - oh my! 中用自己的产品解释了三层边界。当前 LangChain 文档也沿用类似定位。

层 LangChain 产品 主要作用
Framework LangChain 提供模型、Tool、Retriever 和 Agent 抽象
Runtime LangGraph 提供长期运行、有状态 Agent 所需的执行、持久化和中断能力
Harness Deep Agents 在 LangGraph 之上预置规划、文件系统、Subagents、Context Management 和长期任务能力

这个例子也说明三层不是互斥产品：Harness 可以建立在 Runtime 之上，Runtime 又可以复用 Framework 的抽象。具体业务仍然需要自己定义权限、验收标准和预算，不能因为采用了某个框架就默认获得完整的生产可靠性。

总结

Harness Engineering 关注的不是如何让模型“更像人”，而是如何把模型放进一个可观察、可约束、可恢复、可验证的执行系统。

可以先记住下面四句话：

  1. 模型能力不等于系统可靠性；
  2. Agent 的动作必须经过权限和工具契约；
  3. 完成状态必须来自外部证据，而不是模型自评；
  4. Harness 的修改也必须通过 Trace、评测和回归验证。
