Harness Engineering：理解与应用

发表于 2026-07-28 更新于 2026-08-19 分类于 Harness Engineering
Harness Engineering 学习笔记：工程维度、生态产品与实践建议。

三支柱核心问题与判断规则

维度 核心问题 判断规则
Context Engineering Agent 能看见什么信息？看见的信息是否准确精简？ 如果一个机制在”整理 agent 接下来输入的信息”，它属于这一柱
Architectural Constraints Agent 能做什么、不能做什么？动作空间在哪里有边界？ 如果一个机制在”约束 agent 的能力或交互边界”，它属于这一柱
Garbage Collection Agent 能跑多久？成本和资源怎么回收？ 如果一个机制在”清理过期状态 / 限制成本 / 回收资源”，它属于这一柱

来源说明：三维度不是单一作者的原创定义，是本课程综合 Martin Fowler 系博客（Böckeler 2026-04-02）、Anthropic Rajasekaran（2026-03-24）、Phil Schmid（2026-01-05）多来源抽象的工程维度框架。

我们用 Claude Code 完整走一次三维度归类，从定义变成可验证的判断：

  • Context Engineering (输入端：怎么在第一时间把对的资料喂给它)：项目指令文件、检索结果、工具返回值与会话压缩都在决定“Agent 接下来能看见什么”。项目指令文件属于稳定上下文，并不等同于 RAG。

  • Architectural Constraints (控制流：它发疯的时候，你怎么硬生生把它按住)：Hooks、权限确认和子任务隔离都在约束 Agent 的动作边界。Hook 的具体事件数量会随产品版本变化，不宜写成长期固定数字。

  • Garbage Collection (状态流：内存快被撑爆时，怎么有策略地遗忘)：Token / 费用预算、上下文压缩、检查点和必要时开启新会话，都属于资源与状态生命周期管理。压缩和重置不是非此即彼，通常需要结合任务长度与外部状态设计。

Agent Harness 的常见产品形态

截至 2026 年 8 月 19 日，与编码 Agent 相关的产品和框架可以按使用形态粗略分类。这里列的是示例，不是权威排名；产品能力、套餐和模型支持会持续变化。

形态 典型示例 主要特点 适合场景
CLI / 桌面 Agent Claude Code、OpenAI Codex、Aider 可直接操作仓库、Shell、Git 和测试工具 后端开发、批量改造、自动化任务
IDE 原生 Agent Cursor、Windsurf、Cline、Roo Code、JetBrains Junie 贴近编辑器，便于查看 diff 和交互式修改 日常编码、前端开发、结对编程
云端沙箱 Agent Devin、Replit Agent 在托管环境中异步执行任务 远程任务、团队协作、隔离运行
Agent SDK / Runtime LangGraph、DeepAgents、Claude Agent SDK、OpenAI Agents SDK 由团队自行组合工具、状态、权限和验证 自研 Agent 产品与内部平台

选择产品时应比较具体能力，而不是只看“Harness”标签：

  • 是否能限制文件、网络和命令权限；
  • 是否支持检查点、恢复和结构化进度；
  • 是否能运行真实测试并把失败反馈给模型；
  • 是否提供调用日志、成本统计和审计信息；
  • 是否允许替换模型、工具或运行环境。

Claude Code的Harness：全靠人配置

核心本质：全部由人编写、人工配置，没有自动进化能力，所有规则、技能、约束都需要开发者手动写文件，模型只负责推理执行，不会自己生成 / 优化技能。

文件载体：项目目录下的 .claude/ 文件夹 + 项目根目录 CLAUDE.md，全部是文本、markdown、yaml、脚本文件，没有自动生成逻辑

标准Harness目录文件结构

Harness组件拆解

CLAUDE.md（项目顶层系统提示）

纯 Markdown，完全人工手写，Agent 会话启动时自动加载进上下文。 内容示例：

  • 项目架构、技术栈、目录规范
  • 编码规范、命名规范
  • 禁止行为（禁止操作生产库、禁止修改某些文件）
  • 项目业务背景、约束条件

作用：相当于给 Agent 做岗前培训，不会自动更新，人改文件才会变化稀土掘金。

Skills（技能）

每个 Skill 是一个文件夹，内部是人工写的 SKILL.md，封装一套完整的多步骤工作流。

  • 编写：人写 Markdown，写明任务目标、步骤、检查点、判定标准、输出格式。
  • 调用：对话中输入 /skill名称 手动触发；也可由主 Agent 主动加载。
  • ⚠️关键限制：Claude‑Code 不会自动生成 Skill；任务跑完不会自动沉淀成 Skill；需要人观察任务流程，手动提炼写成 SKILL.md；优化 Prompt 也要人手动修改文件。

例子：写一个refactor技能，完整定义重构代码的步骤、审查项、测试流程，后续直接调用该技能完成重构工作博客园。

Hooks（生命周期钩子）

在 Agent 生命周期事件上绑定脚本，全部人工配置 + 写脚本，在事件发生前后自动执行 shell/python 脚本。 触发事件： SessionStart会话启动、PreToolUse调用工具前、PostToolUse工具执行完成后、PreCompact上下文压缩前、UserPromptSubmit用户提交输入、Stop会话结束等。

配置写在settings.json，示例逻辑：

  • PreToolUse：执行 bash 命令前，脚本拦截高危 shell 命令，拒绝执行
  • PostToolUse：代码写完，自动运行格式化、lint 检查脚本

风险：钩子直接运行本机脚本，权限很高；钩子逻辑完全人写，Agent 不能自己新增钩子resources….。

SubAgents（子智能体）

.claude/agents/下人工编写角色 md 文件，定义子 Agent 的角色、能力、约束。

  • 主 Agent 可以派生隔离上下文的子 Agent，并行做子任务：代码审查、写单测、架构分析。
  • 子 Agent 的角色、规则、边界全部是人工写好；Agent 不能自己创建新的子 Agent 角色。

Memory 记忆系统

Claude‑Code 原生记忆模式：

  1. 会话记忆：当前对话上下文窗口，会话结束丢失。
  2. 持久记忆：需要人手动写brain.md或者借助 MCP 记忆工具；不会自动抓取对话轨迹自动生成用户画像。

对比 Hermes：Hermes 会自动做辩证推理生成用户画像；Claude‑Code 必须人手动维护记忆文档。

MCP（Model Context Protocol）

外部工具连接协议，对接数据库、git、API 等外部服务。 通过.mcp.json配置文件，人工配置 MCP 服务地址、参数，扩展 Agent 的外部工具能力，Agent 不会自己发现、新增 MCP 服务腾讯云。

Permissions & Context

  • Permissions 权限：settings.json人工配置，定义文件读写、shell 命令白名单黑名单，管控 Agent 操作边界。
  • Context 上下文管理：Harness 自动做窗口压缩，但是注入的规则、技能内容来源全部是人工编写的文件。

Claude‑Code Harness 完整运行流程

  1. 会话启动：Harness 读取CLAUDE.md + settings + hooks + skills，全部加载进入上下文。
  2. 用户输入任务 → Model 思考，决定调用工具 / 技能。
  3. 触发 PreToolUse 钩子，执行人工编写的校验脚本。
  4. 通过 MCP 调用工具执行任务。
  5. 执行 PostToolUse 钩子，运行检查脚本。
  6. 返回结果给模型。
  7. 任务结束：不会自动生成 Skill，不会自动优化 Prompt，不会自动更新记忆画像；想要复用本次经验，需要人手动提炼，写新的 Skill 或者修改 CLAUDE.md。

Claude‑Code Harness 核心特点总结

  1. 全人工驱动：Skill、Hooks、子 Agent、项目规则全部要人写文件；Agent 只会执行，不会自我产出配置。
  2. 强绑定 Claude 模型：整套 Harness 原生面向 Anthropic Claude；迁移其他模型需要大量改造。
  3. 配置是静态文件：修改能力必须修改磁盘上的 md/json 脚本，运行时不会自我修改配置文件。
  4. 能力扩展方式：人观察 Agent 执行效果，人工补全规则、新增技能、调整钩子。

OpenAI Codex Harness：OpenAI 为编码智能体实现的底层运行时框架

Codex Harness：协议 + 运行时内核优先，Harness 核心逻辑写在 Rust 底层代码，配置轻量化，强调可回放、可审计、沙箱隔离。

重要区分：Codex Harness 不是一堆 Markdown 配置文件；它是一套二进制运行时 + App‑Server JSON‑RPC 协议，配置文件是辅助，不是 Harness 本体。

Codex Harness 分为两大块：

  1. codex‑core（Rust 实现的 Harness 内核）：Agent 主循环、线程管理、沙箱、权限、上下文压缩、事件队列，是 Harness 本体。
  2. App‑Server（JSON‑RPC 协议服务）：向外暴露能力，CLI、TUI 终端、IDE 插件全部作为协议客户端，复用同一套 Harness 内核，一处修改，全部前端生效。

核心顶层抽象概念

  • Thread：会话线程（一级对象，持久保存完整会话状态，脱离模型运行时也可以保存、回放）
  • Turn：一轮 Agent 执行（一次模型调用 + 工具执行的完整周期）
  • Event：事件流（工具调用、输出、审批请求全部输出事件，完整可审计）
  • Submission：外部提交任务给 Harness 的请求体GitHub。

Claude‑Code 是单进程内 Generator 主循环；Codex 把 Harness 能力抽象成网络协议，任何程序只要实现 JSON‑RPC，就可以调用这套 Agent 运行时。

Harness组件拆解

Tools（工具）

Codex Harness 偏向Shell 优先哲学：不会定义巨量细粒度文件工具；模型更多调用底层 shell 命令完成文件读写、检索。

  • 工具定义写在内核代码中，不是写在 markdown；
  • 支持 MCP 协议外部工具接入；
  • 所有工具执行全部跑在隔离沙箱容器，操作副本环境，默认不直接改动本机真实文件；需要确认才同步回原项目（安全优先）。

Claude‑Code：直接操作本机真实文件系统。

Memory 记忆系统

Codex Harness 的记忆不依赖人工写 md 文件。

  1. Thread 持久化：完整会话全部序列化保存，会话断开之后可以重新加载 Thread ID，恢复全部上下文，支持动作回放（rollout），每一步动作都留审计日志CSDN博…。
  2. 原生加密上下文压缩 compact：OpenAI Responses API 提供专用 compact 接口，输出加密压缩的encrypted_content，不是普通文本摘要；隐私保护性更强，token 占用更低。
  3. 没有原生自动技能沉淀；不会自动把执行轨迹生成 Skill。如果要复用流程，需要手动写AGENTS.md。

对比：

  • Claude‑Code 记忆：会话在进程内存；持久记忆依赖人写 brain.md。
  • Hermes：自动从任务轨迹生成程序性记忆 Skill。

Hooks（生命周期钩子）

Codex Harness没有 Claude‑Code 那种用户自定义脚本 Hook。

  • 校验、拦截逻辑绝大多数内置在 Rust 内核，是硬编码安全门（fail‑closed 保守默认）；
  • 用户不能随意挂载 shell 脚本作为钩子；
  • 扩展能力走 MCP 插件，而不是脚本钩子；

设计哲学：把不变量放进底层代码，而不是交给 prompt / 脚本，避免 prompt 污染上下文窗口。

Context 上下文管理器

  • 静态内容（工具定义、基础系统提示）放在 prompt 最前面，充分利用 OpenAI 提示缓存，降低 token 开销。
  • 专用 compact 压缩接口，不是简单文本摘要；生成加密的上下文块，减少上下文长度。
  • 严格控制上下文窗口，会主动裁剪低价值消息，成本感知路由，控制 token 消耗。

Permissions 权限管控

  1. 沙箱容器隔离是底层机制：Agent 运行在拷贝出来的沙箱环境，文件修改不会直接落地到本地源码；需要人工确认才同步变更。
  2. 权限策略绑定在Thread对象：每个线程独立拥有一套沙箱、文件读写、网络、shell 执行白 / 黑名单。

  3. 高危操作强制请求人工审批；默认拒绝危险行为，fail‑closed（拒绝优先）。

  4. 配置文件：AGENTS.md（对比 Claude‑Code 的 CLAUDE.md）

Codex 也有配置文件AGENTS.md，但是定位和 Claude‑Code 的CLAUDE.md完全不一样：

  1. AGENTS.md 是补充，不是 Harness 本体。Harness 内核逻辑不在这个文件；就算删掉 AGENTS.md，Codex Harness 依然完整运行。
  2. 只存放项目业务规则、角色说明；不定义钩子、不定义技能、不定义权限，权限和钩子都在内核。
  3. 早期 OpenAI 尝试让 AGENTS.md 写大量规则，实践发现超长 md 会挤占上下文，反而降低效果，所以现在提倡精简 AGENTS.md阿里云开发…。

Claude‑Code：CLAUDE.md+.claude 目录是 Harness 的核心载体，大量运行时行为来自读取这些磁盘 markdown 文件。

Codex Harness 完整运行流程

  1. 客户端（CLI/IDE）通过 JSON‑RPC App‑Server，创建一个Thread线程对象，设置沙箱、权限策略。
  2. 提交用户任务，生成Submission，开启一轮Turn。
  3. Harness 内核组装 prompt，带上缓存的系统指令、工具定义，调用 Codex 模型。
  4. 如果模型返回工具调用请求：在隔离沙箱执行工具；全部动作输出Event事件流。
  5. 工具返回结果，继续循环下一轮 Turn；高危操作触发人工审批。
  6. 上下文超限，调用专用 compact 接口生成加密压缩上下文。
  7. 全部会话状态保存在 Thread 持久存储，任务结束，完整执行记录可回放审计。

任务结束：不会自动生成 Skill，不会自动优化提示词，不会自动生成用户画像。想要复用流程，需要人手动写 AGENTS.md 或者 MCP 插件。

LangChain DeepAgents

DeepAgents 是 LangChain 推出的开源可插拔 Agent Harness（智能体管控框架），底层基于 LangGraph 状态图引擎，入口函数 create_deep_agent() 就是组装整套 Harness 的工厂函数。

DeepAgents Harness：以 LangGraph 状态图为底座，全部能力以可插拔 Middleware 中间件形式实现；配置文件只是辅助，Harness 本体是代码图与中间件管道。

DeepAgents Harness 整体形态：是一整套运行环境

  1. 运行底座：LangGraph CompiledStateGraph：Agent 主循环、状态保存、checkpoint 断点回放、人在回路中断全部由 LangGraph 提供GitHub。
  2. 扩展机制：Middleware 中间件管道（Harness 的核心），每个 Harness 能力对应一个中间件，可按需开启 / 关闭：
    • TodoListMiddleware：任务规划、todo 任务清单
    • FilesystemMiddleware：虚拟文件系统、大结果上下文卸载
    • SubAgentMiddleware：派生隔离子智能体
    • SummarizationMiddleware：自动上下文摘要压缩
    • SkillsMiddleware：按需加载 SKILL.md 技能
    • MemoryMiddleware：持久记忆 AGENTS.md
    • HumanInTheLoopMiddleware：高危操作人工审批
    • AnthropicPromptCachingMiddleware：提示缓存降成本GitHub
  3. Backend 插件存储层：抽象文件 IO 后端，支持内存临时存储、本地磁盘、LangGraph Store 持久 KV 库，可混合路由（CompositeBackend）GitHub

Harness组件拆解

Tools（工具集）

  • 内置工具：虚拟文件工具read_file/write_file/edit_file/ls/grep；规划工具write_todos/read_todos；子 Agent 调用工具task()；支持 MCP 协议接入外部工具GitHub。
  • 文件系统是虚拟抽象层 Backend：可以跑在内存 StateBackend（临时），也可以映射真实本地目录 FilesystemBackend，也可以持久化 StoreBackend；支持混合路由：工作草稿放内存，记忆放持久存储。

对比：Claude‑Code 直接操作本地磁盘；Codex 默认沙箱副本；DeepAgents 可灵活切换存储后端。

Memory（记忆系统）

两层记忆架构，由MemoryMiddleware实现：

  1. 会话记忆（Checkpointer）：LangGraph Checkpointer（SQLite/Postgres/Redis），保存单条会话完整状态，支持断点恢复、时间旅行回放。
  2. 跨会话长期记忆（Store）：LangGraph Store（KV / 向量库 / SQL），保存用户偏好、项目约定。
  • 静态记忆来源：AGENTS.md，项目级规则，会话启动加载；AGENTS.md 只是输入，不是 Harness 本体，删掉文件框架依然运行。

⚠️限制：DeepAgents 不会自动从任务轨迹自动生成 Skill，没有 Hermes 那种自进化 GEPA 算法；Skill 依然需要人工写SKILL.md。

Hooks（生命周期钩子）

DeepAgents 没有 Claude‑Code 那种直接执行 shell 脚本的 Hook 机制。 Hooks 能力等价物 = Middleware 中间件： 中间件在消息进出图的管道做拦截、修改、校验、日志；实现 Pre‑ToolCall、Post‑ToolCall 拦截逻辑。

  • 可以自定义 Middleware 实现自定义校验拦截；
  • 不允许直接挂载外部脚本文件执行，扩展全部走代码中间件 / MCP 插件。

对比：

  • Claude‑Code：可以写 shell/python 脚本作为 hooks；
  • Codex：安全逻辑硬编码 Rust 内核；
  • DeepAgents：拦截逻辑写在 JS/Python 中间件代码，可插拔。

Context 上下文管理器（Summarization+Offloading）

由SummarizationMiddleware+FilesystemMiddleware共同完成LangChain：

  1. 上下文卸载 Offloading：工具返回结果超过阈值（>20k token），自动把大文本写入虚拟文件系统，不在消息上下文占 token，需要的时候再读取文件。
  2. 自动摘要压缩：上下文接近窗口上限（约 85%），自动对历史会话做摘要压缩。
  3. Prompt 缓存中间件：对静态系统提示、Skill 元信息做模型侧缓存，降低 token 开销。
  4. Skill 渐进加载：只在任务需要时才完整读取 SKILL.md，启动阶段只读取元信息，避免启动上下文膨胀。

Permissions 权限管控

  1. 虚拟文件系统声明式权限规则：配置允许 / 禁止读写的目录路径；
  2. Backend 隔离：可以把 Agent 限制在指定根目录，禁止访问目录外文件；
  3. Human‑in‑the‑Loop 中间件：高危操作触发 interrupt 中断，等待人工审批放行；
  4. 可选沙箱 REPL 执行环境隔离代码执行。

Skills（技能模块）

遵循 Agent Skills 标准，每个技能目录存放SKILL.md，人工编写工作流，和 Claude‑Code 的 SKILL.md 格式兼容LangChain。

  • 加载模式：渐进按需加载，启动仅读元信息，任务触发才加载完整技能内容，节省上下文。
  • 重要限制：没有自动生成 Skill 能力，任务执行完毕不会自动把工作流沉淀成 Skill，需要人工提炼编写 SKILL.md。

SubAgents 子智能体

SubAgentMiddleware提供，主 Agent 可以派生隔离上下文的子 Agent，分配子任务；子 Agent 拥有独立的状态、文件视图。子 Agent 角色配置来自代码参数或者 SKILL.md，Agent 不能自己创建全新子 Agent 角色。

DeepAgents Harness 完整运行流程

  1. 调用create_deep_agent(model=llm, ...)，组装 LangGraph StateGraph，加载全部开启的 Middleware 中间件、Backend 存储、权限规则、skill 目录。
  2. 用户输入任务，进入 LangGraph 图循环。
  3. 消息经过中间件管道：记忆注入、权限校验、加载需要的 Skill。
  4. 调用 Model 得到工具调用请求；经过中间件校验拦截。
  5. 在配置好的 Backend 虚拟文件系统执行工具；超大结果自动 offload 卸载到文件。
  6. 高危操作触发 Human‑in‑the‑Loop 中断，等待人工确认。
  7. 工具结果返回；上下文接近阈值触发自动摘要压缩。
  8. Checkpointer 保存每一步状态，支持会话中断恢复。
  9. 任务结束：不会自动生成 Skill，不会自动优化 Prompt，想要沉淀能力需要人工写 SKILL.md/ AGENTS.md。

Hermes Agent：自我进化，不用人全部手写

Hermes Agent 是 Nous Research 开源的个人 Agent，提供工具调用、记忆、Skills、MCP、子 Agent 和多平台接入等能力。其仓库文档还介绍了按需生成 Skills 的能力。

需要区分两个项目：Hermes Agent 本身是可扩展 Agent；基于 GEPA 的自动技能优化属于另一个实验性项目 Hermes Agent Self-Evolution。因此，不宜把“所有技能都会自动持续进化”写成 Hermes Agent 的默认保证。

  • Model = 传入的任意大模型（只负责思考推理）；
  • Harness = Agent 主循环 + 三层记忆系统 + Skill 自进化引擎（GEPA） + Hooks 插件系统 + Tools/MCP + 权限沙箱 + 上下文管理器 + 多平台网关。

核心模块

  1. AIAgent主循环引擎（conversation_loop.py）：Harness 的核心状态机，完整 Agent 生命周期，模型调用、工具调度、重试、日志、轨迹落盘、中断控制都在这里。
  2. Skill 生命周期子系统：自动生成 Skill、GEPA 进化优化、技能归档 / 淘汰；唯一拥有修改 Skill 磁盘文件能力的 Harness腾讯云。
  3. 三层 Memory 记忆子系统：会话记忆、程序性记忆 (Skill)、长期用户画像记忆（辩证推理自动构建 profile），SQLite SessionDB 持久存储执行轨迹 trajectory。
  4. 插件 / Hooks 系统：pre_llm_call / post_tool_call等生命周期钩子，支持自定义插件；不直接执行外部 shell 脚本，扩展走插件代码 / MCP 协议。
  5. Tools & MCP 工具层：工具注册表、toolset 工具分组；原生完整支持 MCP 协议，对接外部工具；多后端沙箱（本地 / Docker/SSH/Modal）。
  6. Permissions 权限管控：沙箱隔离、目录白名单、高危操作中断审批。
  7. Context 上下文管理：分层系统提示构建、前缀缓存、轨迹压缩、超大输出文件卸载、自动摘要压缩GitHub。
  8. Gateway 网关层：支持 14 + 消息平台接入（飞书、Telegram、CLI、WebUI），多渠道消息统一送入 Harness 主循环。

磁盘目录：~/.hermes/

Harness组件拆解

Tools（工具集）

  • 内置 40 + 核心工具，采用toolset 分组管理（core、browser、delegation 子 Agent、kanban 看板等），按需开启关闭工具集。
  • 原生 MCP 协议深度集成，config.yaml配置 MCP 服务，接入数据库、github、文件系统等外部工具，不需要修改代码。
  • 多沙箱后端：本地、Docker、SSH、Modal、Daytona；执行环境可切换；Agent 可以运行在远程服务器沙箱，不污染本机环境。
  • 子 Agent 工具：delegate_task()，派生隔离上下文的 SubAgent，拆分复杂任务。

对比：

  • Claude‑Code：直接操作本机文件；hooks 可执行 shell 脚本。
  • Codex：默认沙箱副本，确认才落盘。
  • DeepAgents：Backend 抽象存储。
  • Hermes：多沙箱后端，MCP 原生深度支持。

Memory 记忆系统（Hermes 最大特色：三层记忆）

  1. Episodic 记忆（情景记忆）：session.db SQLite，完整保存每一轮执行轨迹 trajectory，全量历史会话，支持检索回放。
  2. Procedural 记忆（程序性记忆）= Skill 技能：Harness 自动把任务轨迹提炼生成 SKILL.md 写入磁盘。复杂任务结束，后台反思判断：这个流程是否值得沉淀为可复用 Skill；满足条件自动生成 skill 文件。
  3. Semantic 记忆（语义 / 用户画像记忆）：辩证推理自动分析历史交互，提炼用户偏好、项目习惯，自动构建用户 Profile 画像，存入数据库；会话启动自动注入上下文。

⚠️对比其他框架：

  • Claude‑Code、Codex、DeepAgents：Skill、用户记忆全部需要人工写 md 文件，框架不会自动生成。
  • Hermes：Harness 运行时可以自动写 / 更新磁盘上 Skill 和记忆文件；人也可以手动编辑，两者兼容。

Hooks（生命周期钩子 / 插件系统）

Hermes Harness 没有 Claude‑Code 那种直接运行外部 shell 脚本的 Hook。

  • 提供插件回调点：pre_llm_call、post_tool_call、on_session_end、pre_compress等生命周期事件，Python 插件拦截、校验、修改消息流。
  • on_session_end会话结束钩子是自进化闭环入口：任务结束触发后台反思，判断是否生成新 Skill，是否触发 GEPA 优化已有 Skill。
  • 扩展工具优先走 MCP 协议，而不是脚本钩子。

对比：

  • Claude‑Code：可挂载 shell/python 脚本作为 hooks。
  • Codex：安全逻辑硬编码 Rust 内核，无用户自定义脚本钩子。
  • DeepAgents：Middleware 中间件管道拦截。
  • Hermes：Python 插件回调 + 会话结束钩子触发自进化闭环。

Context 上下文管理器

  1. 分层系统提示构建：stable（框架固定）→ context（项目 / 技能）→ volatile（记忆、用户画像）分层拼接，充分利用模型前缀缓存，降低 token 开销GitHub。
  2. 轨迹压缩器 trajectory_compressor：会话接近窗口上限，自动做摘要压缩；大工具输出支持卸载写入虚拟文件，不在消息上下文占 token。
  3. Skill 渐进加载：启动只读取 Skill 元信息；任务真正需要才加载完整 SKILL.md，减少初始上下文膨胀。

Permissions 权限管控

  1. 沙箱隔离：可配置 Docker / 容器执行环境，限制文件读写目录白名单。
  2. 工具集开关：可以禁用高危 bash、文件删除工具。
  3. 高危操作 Interrupt 中断，等待人工审批放行。
  4. 模型无关，权限策略和 LLM 完全解耦。

Skill 自进化引擎（GEPA，Hermes Harness 独有的核心闭环）

GEPA：Genetic‑Pareto Prompt Evolution，遗传‑帕累托提示进化算法，属于 Harness 运行时的一部分，不需要微调模型权重，只迭代优化 SKILL.md 提示词文本。

完整 Skill 生命周期，全部由 Harness 驱动：

  1. Skill Creation（自动生成）：任务完成，on_session_end 钩子触发后台反思，读取完整执行 trajectory，提炼工作流程，生成SKILL.md写入~/.hermes/skills/目录。
  2. Skill 调用：遇到同类任务，Harness 自动检索、加载对应 Skill 执行。
  3. GEPA 自动优化：当 Skill 执行失败 / 用户反馈不好，或者定期后台巡检；GEPA 对 Skill 提示词做变异、沙箱验证评估、帕累托筛选，输出优化后的 Skill，更新磁盘上的 SKILL.md，保留版本历史。
  4. Skill 生命周期管理：技能 active → stale（陈旧）→ archived 归档；长期不用的技能自动归档，避免上下文膨胀。

关键点：全部发生在 Harness 运行时，不需要人手动修改文件；人依然可以手动编辑 SKILL.md，人工修改会参与后续 GEPA 迭代。

Hermes‑Agent Harness 完整运行流程

  1. 消息从网关（CLI / 飞书 /web 等）送入 Harness，初始化 AIAgent 主循环，加载权限、沙箱、插件、MCP 服务。
  2. 加载三层记忆：注入用户画像、相关历史 Skill；构建分层 system prompt。
  3. 用户任务进入循环；插件 pre_llm_call 做前置校验。
  4. 调用 Model；模型输出工具调用；插件校验工具参数。
  5. 在沙箱执行 Tools/MCP；超大输出卸载到文件。高危操作触发人工 interrupt。
  6. 工具结果返回，进入下一轮 Agent 循环。
  7. 会话结束触发on_session_end钩子：
    • 保存完整执行轨迹 trajectory 进入 session.db；
    • 后台反思：判断本次任务轨迹是否值得生成新 Skill；
    • 检查本次使用过的 Skill 是否表现差，标记送入 GEPA 做提示词优化；
    • 更新用户画像记忆。
  8. GEPA 后台异步运行：生成 Skill 候选版本，沙箱评估，更新磁盘 SKILL.md 文件。

✨和其他 Harness 最大不同：任务结束不是终点，Harness 会后台执行学习闭环，修改本地 Skill 配置文件，下次会话直接复用进化后的能力。

总结

核心公理：Agent = Model + Harness

Model 只是推理引擎（大脑）；Harness 是包裹模型的整套运行管控框架，包含 Tools、Memory、Hooks、Context、Permissions 五大基础组件，决定 Agent 实际行为、安全、记忆、扩展能力。 4 套主流 Harness 对比：Claude‑Code、OpenAI Codex、LangChain DeepAgents、Hermes‑Agent。

Claude‑Code Harness（Anthropic）

  • 本体：磁盘配置文件驱动，CLAUDE.md + .claude/目录（md/json/ 脚本），配置就是运行时核心。
  • 模式：人全权编写 Skill、Hooks、规则；运行时不会自动修改磁盘文件。
  • Hook：支持 shell/python 脚本钩子，灵活度高，直接操作本机文件。
  • 模型：强绑定 Claude。
  • 开源：闭源 SDK。
  • 适合：本地开发，希望用 markdown 简单配置快速搭建编码 Agent。

OpenAI Codex Harness（OpenAI）

  • 本体：Rust 内核 + JSON‑RPC App‑Server 协议，安全 / 权限逻辑下沉底层代码。
  • 模式：AGENTS.md仅做业务补充，删掉文件框架仍可运行；没有自动生成技能。
  • Hook：安全逻辑硬编码内核，不允许用户自定义脚本钩子；扩展走 MCP。
  • 文件：默认沙箱副本环境，确认后才修改真实源码。
  • 模型：强绑定 OpenAI 模型。
  • 开源：CLI 开源，内核闭源。
  • 适合：企业级，重视可回放、审计、强安全管控。

LangChain DeepAgents Harness

  • 本体：LangGraph 状态图 + 可插拔 Middleware 中间件管道，代码组装优先。
  • 模式：AGENTS.md/SKILL.md只是输入，框架本体不依赖磁盘配置；Skill 需要人工编写。
  • Hook：等价能力为自定义中间件，拦截消息流，不执行外部脚本。
  • 文件：Backend 抽象层，可切换内存 / 本地磁盘 / 持久 KV 存储。
  • 模型：模型无关，兼容任意 LLM。
  • 开源：完全开源。
  • 适合：开发者二次开发，需要定制 Agent 流程，自由开关各项能力。

Hermes‑Agent Harness（Nous Research）

  • 本体：Python 主循环 + 独有的自进化闭环引擎 GEPA。
  • 模式：配置文件可读可写；Harness 运行时可以自动生成、更新磁盘上的 Skill 文件。
  • 记忆：三层记忆：情景记忆、程序性记忆 (Skill)、自动生成用户画像。
  • Hook：Python 插件回调，on_session_end会话结束钩子触发自进化闭环；无脚本钩子。
  • 文件：多沙箱后端（本地 / Docker/SSH）；自带多平台消息网关。
  • 模型：模型无关，兼容任意 LLM。
  • 开源：完全开源。
  • 适合：长期持续运行 Agent，希望 Agent 从历史任务中自动沉淀、迭代工作技能。

  • Claude‑Code：人写好全部操作手册，工人照着手册干活；手册不会自己变。
  • Codex：工厂底层安全流水线，手册只是附加说明。
  • DeepAgents：积木式工厂，你插拔模块组装流水线。
  • Hermes：工人干完活，下班之后自己复盘，把干活步骤写成新手册，还会不断改良手册。

官方建议

【建议一】 harness 会过时

“A harness encodes assumptions that go stale. What works for Claude 3.5 may not work for Claude 4.5.”——Anthropic 官方博文（2025‑11‑26 Effective Harnesses for Long‑Running Agents，Justin Young）

翻译：Harness 固化了一组对模型的假设，这些假设会过期。对 Claude 3.5 有效的 Harness，换到 Claude 4.5 可能就失效。

对我们的含义：不要把 Harness 作为一次性架构写死，要像管理软件系统一样持续迭代维护。

排查方法：在固定任务集、权限、预算下做版本回归测试。当指标下滑时，优先检查、裁剪过时约束，而不是继续叠加流程规则。

具体信号 / 行动：

  • 信号：同类任务成功率连续下降 5pp 以上
  • 信号：升级新模型后，原有 Harness 的基准测试结果反而退步
  • 行动：每次模型升级后，执行完整基准测试，与旧版本指标做对比

术语解读

  1. pp：percentage point，百分点。下降 5pp 代表指标绝对值降低 5 个百分点。
  2. harness：智能体运行管控框架，既包含生产环境 Agent 执行框架，也包含批量基准评测调度框架；封装权限、钩子、上下文策略、工具调用、约束规则等整套环绕大模型的工程逻辑。
  3. benchmark：基准测试，固定测试数据集，量化 Agent 能力，用于版本横向对比。

业务含义说明 这是 Harness‑Model 匹配度监控策略。 指标下滑不一定是新版本模型本身能力退化；很多场景下模型能力变强，但旧 Harness 中过时的约束、拦截逻辑、上下文策略变成枷锁，阻碍任务执行，造成指标下跌。需要通过基准测试提前识别该类问题。

【建议二】 Build to Delete（建造以便删除）

“The best harness is the one you’re most willing to throw away and rewrite. The dataset of failures from your current harness is more valuable than the harness itself.”——Phil Schmid 博文 2026‑01‑05（Bitter Lesson 三原则之一）

翻译：最好的 Harness，是你敢于舍弃、愿意重写的那一个。当前 Harness 产出的失败样本数据集，比 Harness 框架本身更有价值。

对我们的含义：不要为 Harness 堆砌舍不得删除的复杂度。随着模型、工具、任务变化，过去的保护约束，可能转变为任务的阻碍。

后果：模型能力提升后，过时的刚性控制流会降低任务成功率，同时抬高维护、调试成本。

具体信号 / 行动：

  • 信号：修复一个 bug，需要改动 5 处以上刚性流程，代表系统耦合过重，应当考虑重构
  • 行动：将失败日志作为一等公民长期保存；Harness 框架代码可以迭代甚至废弃，但业务数据、失败样本不能丢弃

术语与理念解读

  1. 刚性流程：代码耦合严重，单点改动引发多处连锁影响，修改成本高，极易引入次生 bug，是系统需要重构的典型信号。
  2. failure log（失败日志）：任务失败原始日志，用于定位问题、沉淀测试用例，属于核心长期资产。
  3. harness：Agent 运行 / 评测工程载体，框架代码可以随时重构、废弃。
  4. 核心思想：上层工程框架会随时代迭代消亡；原始业务数据、失败样本具备长期价值。

【建议三】 三类设计取舍没有唯一答案

Harness Engineering 领域仍在快速演进，下面三组权衡，应当基于业务任务数据来决策，没有普适标准答案：

  1. 单 Agent 循环 vs 多 Agent 分治
    • 单循环：结构简单，状态集中；长任务容易出现上下文膨胀。
    • 多 Agent：隔离性好；但带来任务协调、重试、结果合并的额外成本。
  2. 压缩上下文 vs 新会话恢复
    • 上下文压缩：保留部分历史，但摘要存在丢失细节风险。
    • 新建干净会话：依赖 Checkpoint、进度文件、Feature List 恢复关键状态。
  3. CLI‑first vs IDE‑native
    • CLI：适合脚本化、批量任务、长时间后台运行。
    • IDE‑native：适合高频交互，便于查看 diff、获得可视化反馈。

正确做法：不盲从某厂商固定路线，在相同任务集下对比：成功率、人工干预次数、成本、时延、可审计性，基于业务数据做选型。

结合前面 Claude‑Code / Codex / DeepAgents / Hermes：

  1. Claude‑Code 大量行为写死在 md 配置，非常容易出现 Harness 假设过期；模型升级后旧的 skill、约束会变成阻碍，正好对应建议一。
  2. Build to Delete 启示：不要过度堆砌 Hooks、中间件、Skill；模型变强，很多旧约束要敢于删除；失败轨迹（Hermes 的 trajectory、DeepAgents 的 checkpoint）是核心资产。
  3. Hermes 自进化 Harness 也要受这两条约束：GEPA 自动迭代 Skill，本质就是在持续修正过期假设；但依然要做 benchmark 回归，自进化不能完全替代人工评估。
