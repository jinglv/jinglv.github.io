Harness Engineering：故障点的应对机制

发表于 2026-07-20 更新于 2026-09-08 分类于 Harness Engineering
Harness Engineering 学习笔记：八类常见故障及其运行控制、工具契约、状态恢复、权限、验证与预算机制。

上一节介绍了裸奔智能体的八类常见故障。本章不再把“换一个更强的模型”当作默认答案，而是从 Harness 的角度，为每类故障补上模型外部的工程约束。

本文采用下面八个机制：

  1. Runtime Control：让循环一定有出口；
  2. Tool Contract：让工具失败可见、可分类；
  3. Checkpoint & Task Ledger：让长任务可以恢复；
  4. Context & Cache Management：让上下文保持在预算内；
  5. Permission & Sandbox：让高风险动作不能越权；
  6. Verification & Evaluation：让“完成”必须有外部证据；
  7. Subagent Isolation：让独立子任务隔离上下文；
  8. Budget & Observability：让资源消耗可限制、可追踪。

这些机制不是严格的一一对应关系。例如任务拆解既能帮助状态恢复，也能缓解上下文压力；但“有帮助”不等于“能替代”。Subagent 可以减少主 Agent 的上下文污染，却可能增加整个系统的 Token 消耗。

机制与故障对照矩阵

  • 主解：直接约束该故障；
  • 辅助：只能缓解，不能单独解决；
  • 可能增加：使用不当时会放大该问题。

1. Runtime Control：让 Agent Loop 一定有出口

故障症状：Agent 使用 while True 不断调用模型和工具；模型没有正确结束，系统也没有强制停止条件。

一句话定义：把一次 Agent 迭代组织成 Gather Context（收集上下文）→ Take Action（执行动作）→ Verify（验证结果）→ Repeat（决定继续或退出），并由 Harness 设置最大轮数、超时、预算和明确的终止状态。

Anthropic 在 Building agents with the Claude Agent SDK 中将基本反馈循环描述为 Gather context、Take action、Verify work、Repeat。本文将它称为“四阶段循环”，这是便于讲解的工程抽象，不是固定的行业标准。

这里真正重要的不是 for 比 while 更高级，而是 Harness 不把停止权完全交给模型。

“模型没有继续调用工具”也不能直接等价为“任务成功”。系统还需要区分：

  • 正常完成；
  • 达到最大轮数；
  • 达到最大输出长度；
  • 预算耗尽；
  • 超时；
  • 模型拒绝；
  • 等待用户输入；
  • 验证失败。

生产环境还应增加

  • 单次模型调用和工具调用超时；
  • 连续重复同一动作的检测；
  • 长时间无有效进展的检测；
  • 重试次数与退避策略；
  • 用户取消信号；
  • 每种停止原因的日志和指标。

2. Tool Contract：让工具失败成为一等结果

故障症状：工具抛出异常后，上层统一返回空字符串；模型无法区分“执行成功但结果为空”和“工具执行失败”。

一句话定义：为每个工具定义稳定的名称、参数 Schema、返回结构和错误分类，并将错误以机器可识别的形式返回。

结构化错误不一定非要是某个固定 JSON 字典。关键是协议里必须有明确的失败信号，例如 Claude Tool Result 的 is_error，或 MCP Tool Result 的 isError。

最小工具包装器

一个可靠的工具结果至少要回答

  1. 调用了哪个工具、对应哪个 tool_call_id；
  2. 调用是否成功；
  3. 失败属于参数、权限、超时、临时故障还是永久故障；
  4. 是否值得重试；
  5. 输出是否被截断，完整 Artifact 在哪里。

Tool Contract 解决的是“系统是否正确报告工具执行结果”。它不能证明整个任务已经完成，任务级正确性还要交给 Verification。

3. Checkpoint & Task Ledger：让长任务可以恢复

故障症状：Agent 运行半小时后进程中断；代码可能已经改了一半，但系统不知道完成了什么、验证了什么、下一步是什么。

一句话定义：将任务状态、完成证据和下一步动作持久化，并把它与代码版本关联，使新 Session 可以从最近一个可靠检查点继续。

Anthropic 在 Effective Harnesses for Long-Running Agents 中使用 progress 文件、feature list 和 Git commit 帮助跨 Session 恢复。

Task Ledger 应记录什么

Feature 应当是一个可以端到端验收的功能切片，而不是“读文件”“改文件”“跑测试”这样的操作步骤。

读取测试、修改实现和运行 pytest，是完成 CALC-001 的内部步骤，不应该被拆成三个互相隔离的 Feature。

原子保存最小实现

os.replace 可以避免进程在写文件中途退出后留下半截 JSON。真实系统还应保留上一份有效 Checkpoint，而不是在解析失败后静默从零开始。

不要保存“思考过程”

Progress 文件应该保存：

  • 已完成动作；
  • 当前 Feature；
  • 修改过的文件；
  • 外部验证证据；
  • 最近错误；
  • 下一步动作；
  • 对应的 Git commit。

它不需要保存模型完整的内部推理。可恢复性依赖的是结构化状态和外部证据，而不是一段冗长的思维记录。

Checkpoint 的边界

如果工具已经产生副作用，但进程在保存状态前崩溃，恢复后可能重复执行。因此支付、发送消息、创建资源等操作还需要幂等键或操作日志，不能只靠一个 JSON 文件。

4. Context & Cache Management：控制工作区，而不是堆积历史

故障症状：Messages 不断增长，直到超过上下文窗口；或者动态信息被放进可缓存前缀，导致每轮都重新处理相同的大段内容。

一句话定义：为输入、输出和工具结果设置 Token 预算；保留稳定前缀、当前任务和近期工作集，将较旧历史压缩为结构化交接摘要。

Anthropic 的 Automatic Context Compaction Cookbook 展示了在接近窗口上限时总结历史、清理上下文并继续运行的方式。

Context Window 不是长期记忆

可以把它理解为办公桌：

  • 当前任务和最近工具结果放在桌面；
  • 长期状态放进 Task Ledger、数据库或 Artifact；
  • 旧历史压缩成可验证的交接摘要；
  • 需要时再从外部存储按需读取。

压缩时应该保留什么

这是厂商无关的教学伪代码。不同 API 对 System Prompt、Tools、Messages 和 Cache Breakpoint 的表达方式不同，接入时应使用对应厂商的原生格式。

Prompt Cache 的准确理解

Prompt Caching 通常依赖缓存断点之前的前缀匹配。因此更稳妥的原则是：

  • 稳定策略、工具定义和长文档放在可复用前缀；
  • 当前时间、用户输入、task ID 和本轮状态放在动态后缀；
  • 不要在希望缓存的前缀中插入每轮变化的数据；
  • 通过 API Usage 字段验证是否命中，不要凭感觉判断。

不同厂商的 Usage 字段不同。例如 Anthropic 使用 cache_read_input_tokens、cache_creation_input_tokens 等字段；其他 API 可能使用 cached_tokens。缓存对延迟和费用的影响取决于模型、缓存长度和计费规则，不能统一概括为“翻倍”。

5. Permission & Sandbox：让能力服从最小权限

故障症状：Agent 可以写入任意路径、执行任意命令、访问不必要的密钥，甚至在没有确认的情况下执行删除、发布或支付操作。

一句话定义：默认拒绝，只向任务开放必要的目录、工具和网络能力；高风险动作在执行前进入确定性的权限检查或人工审批。Claude Agent SDK 的 Permissions 也将工具可用性、权限模式和运行时授权作为独立控制面。

路径边界最小实现

命令执行原则

  • 参数使用数组，不拼接 Shell 字符串；
  • 默认 shell=False；
  • 使用命令 Allowlist；
  • 固定工作目录和环境变量；
  • 不把生产密钥暴露给不需要它的工具；
  • 对删除、发布、转账、外发消息等动作要求人工确认；
  • 文件、网络和进程权限尽量放在操作系统或容器边界执行，而不只写在 Prompt 里。

Prompt 中的“请不要删除文件”只是一条模型指令；Sandbox 和权限检查才是模型无法绕过的系统边界。

6. Verification & Evaluation：完成必须有外部证据

故障症状：Agent 修改了代码后直接宣布“已经修复”，没有运行测试；或者只依赖另一个 LLM 阅读文本并给出主观批准。

一句话定义：把验收标准转成可执行检查，验证失败就带着诊断结果进入有上限的修复循环，验证通过后才更新 Task Ledger。

确定性验证优先

完整日志可以保存为 Artifact，只把摘要放进 Context，避免一次失败输出占满窗口。

真正的 Verification Loop

“Loop”意味着验证失败后会重新修复、重新验证，并且重试次数有上限，而不是只调用一次测试函数。

不要把测试规则写得过于绝对

Mock 是正常的单元测试技术，问题在于只用 Mock 验证本应进行集成或端到端测试的关键路径。

同样，规则不应该是“任何测试都禁止修改”，而应该是：

禁止为了掩盖实现缺陷而删除、跳过或放宽既有验收测试。需求确实变化时，测试修改需要说明理由并接受独立评审。

Evaluator 是补充，不是证据本身

对于 UI 观感、文案质量或开放式产物，可以加入独立 Evaluator：

  1. Planner 生成任务和验收标准；
  2. Generator 生成产物；
  3. 自动化工具收集测试、浏览器、API 或数据库证据；
  4. Evaluator 根据标准和证据评估；
  5. 不通过则将反馈返回 Generator；
  6. 达到最大评估轮数后失败退出。

Anthropic 在 Harness Design for Long-Running Application Development 中将这种模式描述为受 GAN 启发的 Planner、Generator、Evaluator 三角色架构。但它没有 GAN 的训练、损失函数或参数更新，更准确的称呼是“角色分离与独立评估”。

另一个 LLM 的批准仍然是随机判断，不能替代 pytest、类型检查、静态分析、浏览器操作或人工审批等外部证据。

7. Subagent Isolation：隔离上下文，而不是复制混乱

故障症状：主 Agent 同时处理多个独立问题，工具日志和试错过程互相污染，导致 Context 迅速膨胀。

一句话定义：把边界清晰、可以独立验收的子任务交给独立 Context；主 Agent 只接收结构化结果和必要证据。

主 Agent 不需要接收子 Agent 的全部中间日志，但也不应该只接收一句“已经完成”。至少应返回：

适合交给 Subagent 的任务

  • 相互独立的代码调查；
  • 针对单个模块的修改；
  • 独立测试和审查；
  • 大量中间输出但最终结果很短的研究任务。

不适合拆分的任务

  • 下一步立即依赖结果的阻塞任务；
  • 多个 Agent 会同时修改同一文件的任务；
  • 需要共享大量隐含上下文的小任务；
  • 任务价值低于额外编排成本的场景。

Subagent 是上下文隔离和并行化机制，不是成本控制机制。多个 Agent 会重复读取信息、调用模型和使用工具，总费用可能明显上升。因此每个 Subagent 都应有独立的工具权限、最大轮数和预算。

8. Budget & Observability：让成本有硬上限

故障症状：系统只限制了单次输出，却没有限制整个任务的调用次数、Token、工具执行时间或费用；发生死循环时只能等账单报警。

一句话定义：在任务开始前定义资源预算，每轮执行前检查硬限制，同时记录能解释成本和失败原因的运行指标。Claude Agent SDK 的 Cost tracking 也分别提供成本追踪、预算限制和最大轮数控制。

最小预算检查

调用模型和工具之前检查预算，可以避免已经超限后才停止。真实系统还应为单个 Subagent、单个工具和整个父任务分别设置预算。

至少记录这些指标

Runtime Control 的最大轮数只能减少最坏情况，不能代替成本预算。Budget 负责“不能超过多少”，Observability 负责“为什么花了这些资源、在哪里失败”。

可以同时设置：

  • 硬限制：超过后立即停止；
  • 软阈值：达到 70% 或 90% 时压缩上下文、降低并发或请求用户确认；
  • 异常告警：单轮 Token、工具延迟或失败率突然升高时记录并告警。

总结：Harness 的价值是建立不可绕过的不变量

八个机制最终可以收束成八条工程不变量：

  1. 循环一定有出口；
  2. 工具失败一定可见；
  3. 任务中断后一定可以从可靠状态恢复；
  4. 上下文一定受预算约束；
  5. 高风险动作一定经过权限检查；
  6. 完成状态一定有外部证据；
  7. 子任务隔离不能丢失结果和证据；
  8. 资源消耗一定可限制、可解释。

模型负责提出下一步动作，Harness 负责决定这个动作是否允许执行、执行结果是否可信、任务是否真的完成，以及系统什么时候必须停止。这才是 Harness Engineering 相比单纯 Prompt Engineering 多出来的工程价值。
