从 Prompt 到回答：一次 LLM 请求经历了什么？

发表于 2026-10-04 分类于 大语言模型
从消息输入、Chat Template 和 Token 化开始，逐步理解 Prefill、Logits、解码策略、KV Cache、Decode 循环以及最终文本输出。

从 Prompt 到回答：一次 LLM 请求经历了什么？

在上一篇文章中，我们已经知道：大语言模型会根据已有上下文不断预测下一个 Token。

但当我们在聊天框中输入一句话，或者调用一次模型 API 时，这句话并不会直接进入 Transformer，模型也不会一次性在内部“写出”整段回答。

一次典型的 LLM 请求，需要依次经历：

消息输入 → 聊天模板 → Token 化 → Prefill → Logits → 解码策略 → Decode 循环 → 停止与文本输出

本文将沿着这条链路，完整走读一次请求从自然语言输入到模型回答的过程，并使用 Qwen/Qwen2.5-0.5B-Instruct 编写一个可以本地执行的示例。

从两个层次理解一次 LLM 请求

“LLM 请求”通常包含两个不同层次：

  1. 应用层请求：客户端将消息、生成参数等内容发送给本地程序或远程推理服务；
  2. 模型推理过程：推理服务把消息转换成 Token，调用模型计算，并逐个生成输出 Token。

层次 处理内容 常见工作
客户端 用户问题与调用参数 构造请求、身份验证、发送请求、接收流式结果
推理服务 请求调度与预处理 校验参数、选择模型、批处理、应用聊天模板
Tokenizer 文本与 Token ID 转换 编码输入、插入特殊 Token、解码输出
模型 数值张量 Prefill、计算隐藏状态、输出 Logits
解码器 Logits 与生成参数 Greedy、Sampling、Top-k、Top-p、停止判断

下面重点介绍推理服务接收到消息之后，模型内部发生的过程。

第一步：接收消息与生成参数

一次对话请求通常不只有当前问题，还可能包括：

  • System Message：规定模型角色、行为边界和输出要求；
  • 历史对话：此前的 User 与 Assistant 消息；
  • 当前问题：用户本轮输入；
  • Tool Message：工具调用返回的结果；
  • 生成参数：最大输出长度、Temperature、Top-k、Top-p 等。

第四步：Embedding 与位置信息

Token ID 只是词表编号，不能直接表达语义。模型首先通过 Embedding 层把每个 Token ID 映射为高维向量。

模型还需要知道每个 Token 在序列中的位置。现代 LLM 通常会使用 RoPE 等位置机制，将位置信息引入注意力计算。

经过这一步，模型处理的已经不再是文字或整数编号，而是多维数值张量。

第五步：Prefill 处理全部输入

Prefill（预填充）阶段会一次处理输入上下文中的全部 Token。

假设输入长度为 35 个 Token，模型会对这 35 个位置进行 Transformer 计算，得到每个位置的隐藏状态，并根据最后一个位置的隐藏状态计算第一个待生成 Token 的 Logits。

Prefill 同时会建立 KV Cache，缓存每一层注意力中已经计算出的 Key 和 Value。

需要区分：

  • Prefill 可以并行处理输入中的多个 Token；
  • 后续 Decode 具有自回归依赖，通常需要逐个生成 Token。

输入越长，Prefill 需要处理的 Token 越多，首个输出 Token 出现前的等待时间通常也越长。这段时间常用 TTFT（Time To First Token，首 Token 延迟）衡量。

第六步：模型输出 Logits

模型最后一层的隐藏状态会经过 Language Model Head，映射成与词表大小相同的一组分数。

假设模型词表有 151,936 个 Token，那么每次预测都会产生 151,936 个 Logits：

Logits 是未经归一化的原始分数，不是概率。对 Logits 应用 Softmax 后，才能得到总和为 1 的概率分布：

例如：

候选 Token Logit 概率示意
“Token” 4.8 52%
“词元” 4.1 26%
“模型” 3.2 11%

这些数字只用于说明概念。真实结果会受到完整上下文、模型参数以及生成配置的影响。

还要再次强调：某个 Token 的生成概率更高，只代表它更符合模型学到的语言分布，不代表它表达的事实一定正确。

第七步：解码策略选择下一个 Token

模型产生概率分布之后，还要由解码策略决定实际输出哪个 Token。

解码方法 工作方式 结果特点
Greedy 始终选择分数最高的 Token 确定性强，但可能缺乏多样性
Sampling 按概率随机选择 Token 结果更加多样
Temperature 调整概率分布的集中程度 越高通常越随机
Top-k 只在概率最高的 k 个候选中采样 限制候选数量
Top-p 在累计概率达到 p 的候选集合中采样 候选规模随分布变化

如果启用采样，则通常还需要进行 Temperature 缩放、Top-k 或 Top-p 过滤，然后从处理后的概率分布中抽样。

第八步：Decode 循环与 KV Cache

选择出第一个输出 Token 后，生成还没有结束。这个 Token 会被追加到已有序列中，模型继续预测下一个 Token：

如果没有 KV Cache，模型每生成一个新 Token，都需要重新计算整个历史序列。KV Cache 保存了历史 Token 在各注意力层中的 Key 和 Value，使后续步骤可以复用这些结果。

典型 Decode 步骤如下：

  1. 输入上一轮选出的新 Token；
  2. 读取历史 KV Cache；
  3. 计算新 Token 对应的 Query、Key 和 Value；
  4. 将新的 Key、Value 追加到缓存；
  5. 得到下一 Token 的 Logits；
  6. 使用解码策略选择 Token；
  7. 重复以上过程。

KV Cache 减少了重复计算，但会随着上下文增长占用更多内存。因此，长上下文不仅受到上下文窗口限制，也会带来更高的显存或内存消耗。

第九步：判断是否停止生成

生成循环不会无限进行。常见停止条件包括：

停止条件 说明
EOS Token 模型生成了序列结束标记
Stop Sequence 输出命中了应用配置的停止字符串或 Token 序列
max_new_tokens 达到允许新增的最大 Token 数
自定义规则 业务代码定义的停止条件

需要注意，max_new_tokens 限制的是新生成 Token 的数量，不包含原始输入长度。

生成结束后，Tokenizer 会把输出 Token ID 解码为文本：

如果接口启用了流式输出，服务端通常会在生成过程中逐步将新内容发送给客户端，而不是等待完整回答生成后一次性返回。

完整流程总结

阶段 输入 输出 核心作用
消息输入 System、User、历史消息 消息列表 提供任务和上下文
Chat Template 消息列表 格式化序列 添加角色和消息边界
Tokenizer 格式化序列 Token ID、Attention Mask 转换为模型输入
Embedding Token ID 高维向量 提供数值表示
Prefill 全部输入向量 首次 Logits、KV Cache 理解输入并建立缓存
解码策略 Logits 下一个 Token 决定本轮实际输出
Decode 新 Token、KV Cache 新 Logits、更新后的缓存 逐 Token 生成
停止与解码 生成 Token 序列 文本回答 结束生成并返回结果

流式输出是如何实现的？

模型内部仍然是逐 Token 生成。所谓流式输出，是推理服务在生成过程中不断把已经解码的新增内容发送给客户端。

因此，流式输出通常不会让模型更早完成整段回答，但可以让用户更早看到首个结果，改善交互体验。

流式输出还需要处理一个细节：单独一个 Token 不一定能立即解码成完整字符。一些实现会暂存尚未形成完整文本的字节片段，再将可显示内容发送给客户端。

一次请求中的时间都花在哪里？

一次 LLM 请求的延迟大致来自以下部分：

阶段 可能的耗时来源
网络传输 请求体大小、网络距离、连接建立
排队与调度 并发请求数量、批处理策略、服务负载
Token 化 输入长度、Tokenizer 实现
Prefill 输入 Token 数、模型规模、计算设备
Decode 输出 Token 数、KV Cache、解码策略
文本后处理 增量解码、内容检查、格式校验

常见性能指标包括：

指标 含义
TTFT 从请求开始到产生首个输出 Token 的时间
TPOT 生成阶段平均每个输出 Token 所需时间
Tokens/s 每秒生成的 Token 数量
End-to-End Latency 从发送请求到完整响应结束的总时间

通常来说：输入越长，Prefill 成本越高；输出越长，Decode 循环次数越多。

常见误区

误区一：模型直接读取了用户输入的文字

模型实际处理的是经过 Chat Template 和 Tokenizer 转换后的 Token ID 与数值向量。角色标记、特殊 Token 和消息边界都会影响最终输入。

误区二：模型一次生成完整回答

典型自回归 LLM 每轮只预测一个新 Token。完整回答来自不断“预测—选择—追加—再预测”的循环。

误区三：概率最高的 Token 就一定正确

概率描述的是模型认为某个 Token 在当前上下文中有多合适，不是事实正确率。语言流畅与事实可靠是两个不同问题。

误区四：KV Cache 是模型的长期记忆

KV Cache 只是一次推理过程中复用注意力计算的缓存。请求结束后，它通常会被释放；它不等于用户记忆、知识库或模型参数。

误区五：上下文越长，模型理解得越好

加入上下文会增加可用信息，也可能引入噪声、冲突信息和更高延迟。上下文窗口表示容量上限，不代表模型能够同等有效地使用窗口中的所有内容。

小结

一次 LLM 请求的核心流程可以概括为：

  1. 应用将 System、User 和历史消息组织成消息列表；
  2. Chat Template 将消息转换成模型约定的序列；
  3. Tokenizer 将文本编码为 Token ID；
  4. Prefill 处理全部输入，计算首轮 Logits 并建立 KV Cache；
  5. 解码策略从候选分布中选择下一个 Token；
  6. Decode 利用 KV Cache 逐 Token 生成后续内容；
  7. 命中 EOS、Stop Sequence 或长度限制后停止；
  8. Tokenizer 将输出 Token ID 解码为最终文本。

理解这条链路之后，后续学习 Tokenizer、解码参数、上下文窗口、结构化输出和模型推理优化时，就能知道每个概念位于整条请求链路的什么位置。
