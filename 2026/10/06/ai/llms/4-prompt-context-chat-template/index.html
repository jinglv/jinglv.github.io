Prompt、Context 与 Chat Template：模型真正看到了什么？

发表于 2026-10-06 分类于 大语言模型

Prompt、Context 与 Chat Template：模型真正看到了什么？

在前两篇文章中，我们已经了解了一次 LLM 请求的完整过程，以及 Tokenizer 如何把文本转换为 Token ID。

接下来会遇到三个经常一起出现、也最容易混淆的概念：

  • Prompt；
  • Context；
  • Chat Template。

用户可能只输入了一句话，但模型真正接收到的内容还可能包括 System Message、历史对话、工具结果、检索资料、角色标记和特殊 Token。

因此：

用户输入的文字，不一定等于模型最终看到的完整输入。

本文将从消息结构开始，介绍 Prompt、Context 和 Chat Template 各自解决什么问题，以及它们如何共同组成模型真正接收的 Token 序列。

先理解三个核心概念

概念 核心含义 典型内容
Prompt 提供给模型的指令、问题或输入 当前问题、任务描述、Few-shot 示例
Context 模型在本次推理中能够利用的全部信息 System、历史对话、当前问题、工具结果、检索资料
Chat Template 将结构化消息转换为模型约定序列的格式规则 角色标记、消息边界、生成起始标记

三者之间的关系可以概括为：

Prompt 到底是什么？

Prompt 通常翻译为“提示词”，但在不同语境中，它的范围并不完全一致。

狭义 Prompt

狭义 Prompt 指用户当前提供的指令或问题：

广义 Prompt

有些文档会把发送给模型的全部输入统称为 Prompt，包括：

  • System 指令；
  • 用户问题；
  • 历史对话；
  • Few-shot 示例；
  • 检索到的文档；
  • 工具说明；
  • 输出格式要求。

因此，看到“Prompt 长度”“Prompt Token”或“Prompt Engineering”时，需要结合上下文判断这里的 Prompt 指当前用户输入，还是指模型的完整输入。

在本文中，为了便于区分：

  • Prompt 主要表示任务指令或输入内容；
  • Context 表示模型本次请求能够看到的全部内容。

Context：模型本轮能够看到的全部信息

Context 可以理解为模型本次推理的“临时工作区”。典型 Context 由以下部分组成：

这些内容经过 Chat Template 和 Tokenizer 处理后，共同占用模型的上下文窗口。

Context 不等于长期记忆

模型不会因为上一轮回答过某个问题，就自动永久记住那次对话。

无状态推理可以简化理解为：

每一轮都需要重新提供模型需要参考的历史消息。

一些聊天产品或 API 看起来“记住”了对话，是因为应用或服务端替用户保存了历史，并在下一次调用时重新组装 Context；也可能使用摘要、数据库或其他外部记忆机制。模型本身只能利用当前请求实际提供给它的信息。

Context Window 是容量上限

Context Window（上下文窗口）表示模型一次推理能够处理的 Token 范围。通常需要同时容纳：

但具体限制方式由模型和推理服务决定。有的服务分别限制最大输入和最大输出，有的服务限制二者总和。

上下文窗口越大，不代表模型就能同等有效地利用其中所有内容。过长 Context 可能带来：

  • 更高的 Prefill 延迟；
  • 更大的 KV Cache；
  • 更高的调用费用；
  • 更多无关信息和冲突信息；
  • 重要内容被埋在大量文本中；
  • 输入被截断的风险。

消息角色分别表示什么？

聊天接口通常使用 role 和 content 表示一条消息：

常见角色包括：

角色 典型作用 常见内容
System 提供整体行为要求和任务背景 身份、边界、风格、约束
User 表示用户指令或输入 问题、数据、修改意见
Assistant 表示模型此前的回答 对话历史、Few-shot 目标回答
Tool 表示工具执行结果 搜索结果、数据库记录、函数返回值

角色是否被支持、具体名称以及序列化方式取决于模型和 Chat Template。不能假设所有模型都原生支持完全相同的角色集合。

System Message

System Message 常用于描述：

  • 模型扮演什么角色；
  • 任务目标是什么；
  • 回答风格和语言；
  • 输出格式；
  • 不允许执行的操作；
  • 可使用的背景信息。

因此，真正的安全控制不能只依赖一句 System Prompt，还需要权限校验、工具白名单、参数验证、沙箱和人工确认等机制。

Assistant Message 也可用于 Few-shot 示例：人为提供理想回答，让模型模仿任务格式和风格。

即使消息内容相同，使用错误模板也可能导致：

  • 模型继续复述用户内容；
  • System Message 失效；
  • 角色混乱；
  • 输出异常的特殊标记；
  • 指令遵循能力下降；
  • 工具调用格式错误。

Chat Template 必须尽量匹配模型训练或后训练时使用的格式。

add_generation_prompt 有什么作用？

add_generation_prompt=True 会让模板在序列末尾添加“接下来由 Assistant 回答”的标记——前提是该模板定义了这种标记。

对于 ChatML 风格，差异可能是末尾多出：

如果模型需要生成起始标记却没有添加，它可能把最后一条 User Message 当作尚未结束的内容继续补全，而不是开始回答。

但并非所有模型都需要独立的 Assistant 起始标记，因此该参数的实际效果取决于具体模板。

continue_final_message 是什么？

通常情况下，我们希望模型在最后一条 User Message 后开始新的 Assistant Message。

另一种情况是：消息列表最后已经包含一个尚未写完的 Assistant Message，希望模型继续完成它。例如：

continue_final_message=True 会让模型续写最后一条消息，而不是创建新的 Assistant Message。这种方式有时称为 Prefill Response。

需要注意：

不要同时设置 add_generation_prompt=True 和 continue_final_message=True。

前者要求开始一条新消息，后者要求继续最后一条消息，语义互相冲突，Transformers 会拒绝这种组合。

保留全部历史 信息最完整 Token 持续增长

常见错误

错误一：把 Prompt 和 Context 当成完全相同的概念

广义用法中 Prompt 可以指完整输入，但在分析系统时，区分当前指令和全部 Context 更清晰。

错误二：认为模型会自动记住聊天历史

模型只能利用当前请求实际包含的消息。所谓“对话记忆”通常由应用保存、筛选和重新注入。

错误三：手动拼接 User: 和 Assistant: 就能适配所有模型

不同模型使用不同角色标记、消息边界和特殊 Token。应优先使用模型自带 Chat Template。

错误四：模板化后再次自动添加特殊 Token

Chat Template 通常已经包含所需特殊 Token。先格式化为字符串再 Tokenize 时，应根据模型文档设置 add_special_tokens=False，避免重复 BOS 或 EOS。

错误五：同时启用 add_generation_prompt 和 continue_final_message

一个表示开始新的 Assistant Message，另一个表示继续最后一条消息，两者语义冲突。

错误六：System Prompt 可以代替程序权限控制

System Prompt 只能引导模型行为，不能代替身份验证、授权、参数校验、沙箱和人工确认。

错误七：把检索文档或工具结果当成可信指令

外部内容可能错误、过时或包含 Prompt Injection。应将其作为数据处理，并限制其影响范围。

错误八：无限保留所有历史消息

历史越长，Token、延迟和成本越高，也可能引入噪声。需要根据任务设计裁剪、摘要或外部记忆策略。

小结

Prompt、Context 和 Chat Template 的关系可以总结为：

  1. Prompt 是提供给模型的指令、问题或输入，但有时也被广义地用于表示全部输入；
  2. Context 是模型本次推理能够看到的全部内容；
  3. System、历史对话、当前问题、检索资料和工具结果都可能进入 Context；
  4. 模型不会自动保留上一轮对话，应用需要重新发送所需历史；
  5. Chat Template 把结构化消息转换为模型训练时使用的序列格式；
  6. add_generation_prompt 通常用于开始新的 Assistant 回答；
  7. continue_final_message 用于续写最后一条消息，两者不能同时使用；
  8. Chat Template 与 Tokenizer 共同决定模型最终接收的 Token ID；
  9. 所有进入 Context 的内容都会占用 Token 预算，并影响延迟、内存和费用；
  10. System Prompt 不是程序级安全边界，外部内容也不是天然可信指令。
