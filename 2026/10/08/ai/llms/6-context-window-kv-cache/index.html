上下文窗口与 KV Cache：模型如何记住前文并高效生成？

发表于 2026-10-08 分类于 大语言模型
从上下文窗口、Prefill 和 Decode 出发，理解 Transformer 为何需要 KV Cache、缓存中保存了什么、如何估算显存，以及长上下文推理中的常见优化策略。

上下文窗口与 KV Cache：模型如何记住前文并高效生成？

在上一篇文章中，我们了解了模型如何通过 Logits、Softmax 和解码策略选择下一个 Token。

不过，生成下一个 Token 时，模型不能只看最后一个词。它还需要参考 System Message、历史对话、当前问题以及已经生成的内容。例如：

要回答“抽屉里”，模型必须能够利用前面的信息。这就引出了两个重要概念：

  • 上下文窗口（Context Window）：本次推理中，模型最多能够处理多少 Token；
  • KV Cache：生成过程中缓存历史 Token 的注意力 Key 和 Value，避免每一步重复计算。

它们都与“前文”有关，但解决的是两个完全不同的问题：

上下文窗口决定模型最多能看多少内容；KV Cache 决定模型重复使用这些内容时能有多高效。

先理解四个核心概念

概念 核心含义 解决的问题
Context Window 一次推理允许使用的最大 Token 范围 模型最多能看到多少内容
Prefill 一次处理输入上下文，并建立初始 KV Cache 理解 Prompt，准备生成第一个 Token
Decode 每次生成一个新 Token 逐步完成回答
KV Cache 保存各层历史 Token 的 Key 和 Value 避免 Decode 时重复计算历史 K/V

输入与最大输出之和就可能超过模型允许的范围。不同框架可能报错、缩短输出，或者按照指定策略截断输入。

需要注意，部分 API 会分别公布最大输入长度和最大输出长度，实际限制应以具体模型和服务文档为准，不能只套用一个加法公式。

Token 数量不等于字数

上下文窗口按 Token 计算，不按汉字数、单词数或文件大小计算。

因此，“支持 128K 上下文”表示大约支持 128K Token，并不等于固定支持 128K 个汉字或英文单词。

超出上下文窗口会怎样？

常见处理方式包括：

处理方式 行为 风险
直接报错 拒绝超长请求 调用失败
从左侧截断 删除最早的 Token System 或关键历史可能丢失
从右侧截断 删除输入尾部 Token 当前问题可能不完整
保留首尾 留下开头规则和最新消息 中间信息可能丢失
摘要压缩 将旧历史总结后再输入 摘要可能遗漏细节
RAG 检索 只加入与问题相关的片段 取决于检索质量

截断是一种应用层策略，不是模型突然获得了额外空间。生产系统应明确决定哪些内容可以删除，不能盲目依赖 Tokenizer 的默认截断。

上下文窗口不是长期记忆

这是最常见的误解之一。

模型能够在当前请求里引用前文，并不意味着它已经把对话永久保存进参数。对普通无状态 API 而言，下一次请求通常仍需要再次提交相关历史：

如果第二次请求只发送“问题 B”，模型未必知道前面讨论过什么。

可以把几个概念区分开：

名称 保存在哪里 生命周期 是否改变模型参数
Context 本次请求的 Token 序列 通常到请求结束 否
KV Cache 推理引擎的内存或显存 通常到序列结束或缓存被回收 否
对话数据库 应用自己的存储系统 由应用决定 否
模型参数 权重文件 训练后长期存在 是，只有训练才会更新

因此：

上下文窗口是模型的“工作台大小”，不是永久记忆容量；KV Cache 是计算缓存，也不是聊天记录数据库。

为什么生成会分成 Prefill 和 Decode？

大语言模型的在线推理通常分成两个阶段。

Prefill：处理输入

Prefill 也叫 Prompt Processing。模型一次接收 Prompt 中的多个 Token，通过 Transformer 的所有层进行计算：

这一阶段可以并行处理多个输入 Token，但自注意力需要建立它们之间的关系。输入越长，Prefill 的计算量和首 Token 等待时间通常越大。

衡量 Decode 速度时，常见指标包括：

  • 每秒生成 Token 数（Tokens/s）；
  • 相邻输出 Token 的时间间隔（Inter-Token Latency，ITL）。

输入规模 一批 Prompt Token 每一步通常 1 个新 Token

KV Cache 行为 创建并填充 读取历史缓存并追加新 K/V
典型瓶颈 长 Prompt 的计算 内存带宽、缓存访问和逐步调度

为什么只缓存 K 和 V？

在 Causal Language Model 中，过去的 Token 不能看未来。因此，已经处理过的历史 Token，其 K 和 V 不会因为后面又生成了新 Token 而改变。

一个容易说错的地方

KV Cache 并没有让每一步 Attention 变成常数复杂度。

生成新 Token 时，新 Query 仍需与可见范围内所有历史 Key 计算注意力，并读取对应 Value。历史越长，本步需要读取的数据通常越多。

KV Cache 省掉的是：

  • 历史 Token 在各层重新产生 K/V 的计算；
  • 历史部分大量重复的 Transformer 前向计算。

它没有消除新 Token 对历史上下文的 Attention 访问。

MHA、MQA 和 GQA 对缓存的影响

Attention 类型 Query Head KV Head KV Cache 特点
MHA 多个 通常与 Query Head 数相同 缓存较大
MQA 多个 通常只有 1 个 缓存显著减小
GQA 多个 少于 Query Head、但多于 1 个 在质量和效率之间折中

现在很多 LLM 使用 GQA，原因之一就是它可以减少 KV Cache 的容量和读取带宽。估算缓存时应读取 num_key_value_heads，不能总是直接使用 num_attention_heads。

两者相关，但不能互相替代：

请求结束后必须永久保留 否 否

上下文越长，通常需要缓存的 K/V 越多：

但增加 KV Cache 容量不会让一个原本只支持 8K 的模型自动变成 128K 模型。模型的位置编码、训练长度、注意力实现和服务限制也需要支持长上下文。

为什么“支持 128K”不等于“128K 都能用好”？

上下文窗口描述的是可接收范围，不保证模型能同等有效地使用窗口中的每一处信息。

长上下文能力还受到以下因素影响：

  • 模型是否在足够长的数据上训练或继续训练；
  • 位置编码及其扩展方式；
  • 重要信息在上下文中的位置；
  • 无关信息对注意力的干扰；
  • 推理精度和缓存量化；
  • 任务是否需要跨很远位置组合信息。

常见 KV Cache 优化方式

Dynamic Cache

Dynamic Cache 随生成长度逐步增长：

它使用灵活，也是 Transformers 中许多模型的默认缓存方式，但不断变化的张量形状可能不利于某些编译优化。

Static Cache

Static Cache 预先分配最大缓存空间：

固定形状更适合 torch.compile 或某些硬件编译器，但短请求可能浪费已分配空间。

Sliding Window Attention

滑动窗口注意力只让某些层关注最近固定数量的 Token：

当缓存达到窗口长度后，相关层不再无限增长。这样可以控制计算和显存，但窗口之外的信息无法被这些局部注意力层直接访问。部分模型会混合全局注意力层与滑动窗口层，具体行为取决于模型架构。

Quantized Cache

缓存量化把 FP16/BF16 的 K/V 压缩为更低位宽：

它更适合显存紧张的长上下文场景。短上下文时，量化和反量化开销可能反而降低速度。

Offloaded Cache

缓存卸载把部分 KV Cache 移到 CPU 内存，需要使用时再传回 GPU。

优点是节省 GPU 显存，代价是增加 CPU-GPU 数据传输，吞吐和延迟可能变差。

Paged KV Cache

在线推理服务中的请求长度各不相同。如果为每条请求预留一大块连续显存，容易出现浪费和碎片。

Paged KV Cache 将缓存拆成固定大小的 Block，并通过映射表组织逻辑上连续、物理上可以不连续的缓存：

这类设计便于动态增长、回收和共享缓存块，是 vLLM 等高吞吐推理系统的重要思想。

Prefix Caching

如果多个请求拥有完全相同的 Token 前缀，可以复用该前缀已经计算好的 KV Cache：

这和单次生成中的 KV Cache 有区别：

  • 普通 KV Cache 复用同一序列已经处理过的历史 Token；
  • Prefix Caching 尝试在多个请求或多次生成之间复用相同前缀。

只有 Token ID 序列以及影响其计算的模型配置一致时，缓存才可以安全复用。仅仅“文字看起来差不多”并不够。

常见误区

误区一：上下文窗口就是模型的长期记忆

上下文只在当前推理中参与计算。是否长期保存用户信息，取决于应用是否使用数据库、摘要、向量检索或其他记忆系统。

误区二：KV Cache 保存了原始聊天文本

KV Cache 保存的是各层 Attention 所需的数值张量，不是可以直接阅读的聊天记录。应用仍需保存原始消息，才能编辑、展示、检索或重新组织对话。

误区三：KV Cache 会修改模型参数

KV Cache 只保存本次推理的中间计算结果，不会执行反向传播，也不会更新模型权重。

误区四：KV Cache 越大，模型能力越强

缓存只能减少重复计算。它不能增加模型知识，也不能突破模型架构和服务规定的上下文上限。

误区五：使用 KV Cache 后，每个新 Token 都是 O(1)

历史 K/V 不需要重新计算，但新 Query 通常仍要与可见的历史 Key 做 Attention，并读取历史 Value。上下文越长，Decode 单步成本通常仍会增加。

误区六：上下文没有超限，模型就不会忘记

信息位于允许窗口内，只表示模型能够接收它，不保证模型一定准确关注、检索和利用它。

误区七：多轮对话一定会自动复用 KV Cache

很多 API 每轮都会重新提交并计算完整历史。跨轮缓存是否存在、缓存多久以及是否计费，由具体服务决定。

误区八：相同文字一定可以复用 Prefix Cache

缓存复用需要 Token 序列和相关计算条件一致。Chat Template、空格、特殊 Token 或 System Message 的变化，都可能让前缀不再相同。

误区九：KV Cache 应该在训练时使用

训练通常需要并行计算完整序列并保存反向传播所需状态，KV Cache 主要面向自回归推理。训练时错误启用缓存可能造成结果或梯度问题。

工程实践建议

  1. 在发送请求前用对应 Tokenizer 统计完整 Chat Template 的 Token 数；
  2. 为输出预留空间，不要让输入占满整个上下文窗口；
  3. 明确历史截断、摘要和 RAG 资料选择策略；
  4. 根据 num_key_value_heads 而不是只看 Attention Head 数估算缓存；
  5. 并发容量规划时同时计算模型权重和每个活跃请求的 KV Cache；
  6. 短请求优先使用默认 Dynamic Cache，不必过早优化；
  7. 形状固定且需要编译加速时，再评估 Static Cache；
  8. 显存不足时评估滑动窗口、缓存量化或 CPU Offload 的质量与延迟代价；
  9. 大规模在线服务可以使用 Paged KV Cache、Continuous Batching 和 Prefix Caching；
  10. Benchmark 应区分 TTFT、ITL、吞吐量和最大并发数，不能只看一次请求的总耗时。

小结

本文的核心结论可以总结为：

  1. 上下文窗口限制一次推理能够容纳的 Token 总量；
  2. 输入中还包括 System、历史消息、工具结果、检索资料和 Chat Template；
  3. 上下文窗口是工作空间，不是模型的长期记忆；
  4. Prefill 处理完整输入并建立初始 KV Cache；
  5. Decode 复用历史 K/V，每一步只为新 Token 追加缓存；
  6. KV Cache 避免重复计算历史 K/V，但不会消除新 Token 对历史的 Attention；
  7. KV Cache 容量随层数、序列长度、Batch、KV Head 数和数据精度增长；
  8. MQA 和 GQA 可以通过减少 KV Head 降低缓存开销；
  9. Dynamic、Static、Sliding Window、Quantized、Offloaded 和 Paged Cache 各有不同取舍；
  10. KV Cache 不增加模型知识，也不能突破模型本身的上下文限制。

理解 Context Window 和 KV Cache 后，我们就能解释几个常见现象：为什么长 Prompt 的首字等待更久、为什么长对话越来越占显存、为什么高并发推理需要精细管理缓存，以及为什么“支持更长上下文”通常伴随着更高的推理成本。
