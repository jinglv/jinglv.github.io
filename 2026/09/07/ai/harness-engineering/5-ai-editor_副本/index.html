基于 Agent Harness 的智能体编程工具：Claude Code 与 Codex

发表于 2026-09-07 分类于 Harness Engineering
从 Agent Loop 与 Agent Harness 的基础概念出发，详细介绍 Claude Code 和 OpenAI Codex 的项目配置、MCP、Skills、权限、子智能体及完整开发闭环。

介绍

过去我们使用 AI 编程工具，通常是把它当作一个代码生成器：输入 Prompt，得到代码，然后由程序员复制、修改、运行和调试。

Claude Code、OpenAI Codex 等新一代智能体编程工具已经不再局限于“生成一段代码”。它们可以进入真实项目，读取仓库上下文，搜索源代码，调用 Shell 和外部工具，修改文件，运行测试，根据失败结果继续修复，并最终交付可以审查的代码变更。

这种变化背后有两个关键概念：

  • Agent Loop：让 Agent 能够持续规划、执行、观察和调整；
  • Agent Harness：为 Agent Loop 提供上下文、工具、权限、状态、验证和反馈环境。

Claude Code 和 Codex 正是这类 Coding Agent / Agent Harness 的代表性工具。

需要先说明一个术语问题：日常讨论中经常会使用“Harness Agent”和“Loop Agent”来帮助区分职责，但从系统架构上看，更准确的表达是：

Agent Loop 是执行机制，Agent Harness 是承载这个循环的运行环境。Claude Code 和 Codex 通常同时包含两者，而不是先运行一个 Harness Agent，再调用另一个独立的 Loop Agent。

本文先介绍 Agent Harness 和 Agent Loop 的基础关系，再分别介绍 Claude Code 与 Codex 在项目开发中如何配置和使用。

一、从传统 AI 到智能体工具

1. 传统 AI 更像“回答问题的工具”

传统对话式 AI 的主要交互方式是：

它可以解释技术、生成函数或给出修改建议，但通常仍然依赖程序员完成后续动作：

  • 找到应该修改的文件；
  • 判断代码是否符合现有架构；
  • 把代码复制到项目中；
  • 运行测试和启动服务；
  • 把报错重新交给模型；
  • 决定何时提交代码。

此时的 AI 主要负责“给答案”，人负责“完成任务”。

2. Agent 更像“完成任务的伙伴”

Agent 的目标不是只返回一段文本，而是在授权范围内完成一组连续动作。

例如用户提出：

为测试平台增加 AI 测试用例生成功能，并补充后端测试。

这意味着 Agent 必须具备四类能力：

  1. 理解：知道任务、项目和约束是什么；
  2. 行动：能够读取文件、执行命令和访问外部系统；
  3. 反馈：能够观察测试、日志、浏览器和 Git 状态；
  4. 持续执行：能够根据反馈进入下一轮，而不是一次回答后结束。

二、Agent Loop：让智能体持续完成任务

1. Agent Loop 的基本结构

Agent Loop 是 Agent 的核心执行机制，可以概括为：

Plan → Act → Observe → Reflect → Repeat

展开以后是：

各阶段的职责如下：

阶段 主要问题 编程任务中的典型动作
Goal 最终要完成什么？ 增加一个功能、修复一个 Bug、完成一次重构
Plan 应该分几步完成？ 找入口、读测试、确定修改范围、安排验证
Act 现在执行什么动作？ 读写文件、运行命令、调用 MCP、委派子任务
Observe 动作产生了什么结果？ 读取命令输出、错误堆栈、页面截图、Git Diff
Reflect 下一步应该怎样调整？ 修复错误、修改方案、补充上下文、重新测试
Done 是否满足验收标准？ 测试通过、构建成功、结果可审查

OpenAI 在 Codex agent loop 的技术拆解中描述了同样的过程：模型可以返回最终消息，也可以请求工具调用；Harness 执行工具，把结果加入上下文，再让模型继续推理，直到模型停止请求工具并返回结果。

因此，一次用户请求并不一定只对应一次模型调用，而可能包含多轮：

2. Loop Agent 不能脱离环境独立工作

只有循环，没有良好的运行环境，Agent 仍然很难完成真实项目。

它可能不知道：

  • 应该先读哪个文件；
  • 项目使用 npm、pnpm 还是其他工具；
  • 哪些目录不能修改；
  • 哪些操作需要用户确认；
  • 测试命令是什么；
  • 什么结果才算完成；
  • 失败后如何恢复。

所以 Agent Loop 解决的是“如何持续执行”，但不负责提供完整的项目环境。这个环境由 Agent Harness 提供。

三、Agent Harness：为 Agent Loop 构建工作环境

1. 什么是 Agent Harness？

Agent Harness 可以理解为围绕模型和 Agent Loop 构建的一整套工程运行环境。

可以用一句话概括两者关系：

Loop 是 Agent 的心跳，Harness 是 Agent 的工作环境。

2. Harness 管理哪些内容？

Context：项目上下文

让 Agent 知道：

  • 项目是什么；
  • 目录结构是什么；
  • 当前任务是什么；
  • 架构如何设计；
  • 应该遵守哪些约定；
  • 当前代码和 Git 状态是什么。

常见载体包括：

  • CLAUDE.md / AGENTS.md；
  • README.md / ARCHITECTURE.md；
  • 项目文档和源代码；
  • Git 历史；
  • 当前任务描述。

Rules：项目规则

告诉 Agent 什么应该做、什么不能做：

  • 使用什么技术栈；
  • 遵循什么编码规范；
  • 修改后运行什么测试；
  • 哪些接口必须保持兼容；
  • 哪些目录不能修改；
  • 哪些操作需要人工确认。

Tools：本地执行能力

常见工具包括：

  • 读取和修改文件；
  • Shell / Terminal；
  • 代码搜索；
  • Git；
  • 测试与构建工具；
  • 浏览器；
  • 日志查看器。

MCP：连接外部世界

MCP 让 Agent 可以连接外部服务，例如：

外部系统 Agent 可使用的能力
GitHub Issue、PR、Actions
Linear 任务管理
PostgreSQL 数据查询
Playwright 浏览器自动化
Sentry 错误监控
Slack 消息通知
企业 API 内部业务系统

Skills：封装专业工作方法

Skill 告诉 Agent 某类任务应该怎样完成，例如：

  • 代码审查；
  • 前端设计与 React 开发；
  • 数据库迁移；
  • 测试用例设计；
  • 故障排查；
  • 发布流程。

Permissions、Hooks 与 Sandbox：限制和控制行为

它们负责：

  • 限制文件读写范围；
  • 限制命令和网络访问；
  • 在危险操作前请求审批；
  • 在工具调用前后执行检查；
  • 在任务完成前自动运行验证。

Git 与 Tests：保存状态并验证结果

Git 提供版本状态和恢复能力，Tests 提供事实反馈。

四、Claude Code：面向项目开发的 Agent Harness

1. Claude Code 是什么？

Claude Code 是面向软件开发的 Coding Agent。它将 Claude 模型与项目上下文、文件和 Shell 工具、权限、MCP、Skills、Hooks、Subagents 以及 Git/Test 反馈组合在一起。

因此，Claude Code 不应只被理解为：

一个可以在终端中生成代码的 Claude。

更准确的理解是：

Claude Code 的价值在于：它可以在真实仓库中持续执行开发任务，而不是只给出代码片段。

7. Hooks、Permissions 与 Subagent

Hooks

Hooks 适合执行确定性动作，例如：

  • 修改文件后运行格式检查；
  • 工具调用前检查危险命令；
  • 任务结束时运行测试；
  • 记录操作日志；
  • 发送完成通知。

如果一项检查“必须执行”，就不应该只依赖模型是否记得，更适合由 Hook 或 CI 强制完成。

Permissions

Permissions 决定 Claude Code：

  • 可以读取哪些文件；
  • 可以修改哪些目录；
  • 可以执行哪些命令；
  • 哪些动作必须询问用户；
  • 哪些动作应该直接拒绝。

需要特别保护：

  • .env 和密钥文件；
  • 生产数据库；
  • 删除操作；
  • 远程 Git Push；
  • 发布和部署命令。

6. Codex MCP：连接外部工具与上下文

Codex 的 MCP Server 通常配置在 config.toml 中。

Codex CLI、IDE 和同一 Host 上的桌面体验可以共享 MCP 配置，但云端或其他运行环境是否可以使用同一个 Server，仍然取决于它是否能访问对应网络、进程和凭据。

MCP 使用时要重点检查：

  • Server 是本地 STDIO 还是远程 HTTP；
  • 凭据从哪里读取；
  • 哪些工具可以自动执行；
  • 哪些写操作需要审批；
  • MCP 输出是否可能包含不可信内容。

7. Sandbox、Approvals 与 Hooks

Sandbox

Sandbox 控制 Codex 运行命令时可以访问的文件系统和网络范围。

典型思路是：

沙箱的目标不是阻止 Agent 工作，而是限制失败时的影响范围。

Approvals

Approvals 决定 Codex 在什么情况下暂停并询问用户。

例如：

  • 写入工作区外目录；
  • 访问受限制网络；
  • 执行高风险命令；
  • 使用需要额外权限的工具；
  • 进行不可逆外部操作。

Hooks

Codex 可以从 hooks.json 或 config.toml 中的 [hooks] 配置加载生命周期 Hook。

Hooks 适合：

  • 执行格式化和静态检查；
  • 记录工具调用；
  • 检查敏感操作；
  • 在任务阶段变化时发送通知；
  • 把组织策略变成确定性流程。

六、Claude Code 与 Codex 的关键差异

Claude Code 和 Codex 都属于 Coding Agent / Agent Harness，但它们的配置载体和产品入口并不完全相同。

能力 Claude Code OpenAI Codex
项目长期规则 CLAUDE.md AGENTS.md，支持目录级分层覆盖
项目配置 .claude/settings.json 等 .codex/config.toml，可信项目中加载
仓库级 Skills .claude/skills/ .agents/skills/
MCP 配置 常见项目配置为 .mcp.json ~/.codex/config.toml 或项目 .codex/config.toml

权限控制 Permissions + Hooks Sandbox + Approval Policy + Permissions + Hooks
状态与并行 会话、Subagents、团队协作能力 Threads / Tasks、Subagents、Worktrees
主要使用方式 以终端和项目工作流为核心 CLI、IDE、桌面与云端任务等多种入口

它们的共同点比差异更重要：

选择工具时，不应只比较一次代码生成效果，更应该比较：

  • 是否适合团队当前的开发入口；
  • 项目规则是否容易维护；
  • Skills 和 MCP 是否能复用现有工作流；
  • 权限和审批是否符合安全要求；
  • 长任务是否容易恢复、并行和审查；
  • 测试、浏览器、日志和 CI 是否能进入反馈闭环。

七、在同一个项目中使用 Claude Code 和 Codex

如果一个项目需要同时支持 Claude Code 和 Codex，可以让两者读取同一套工程事实，但使用各自的入口配置。

为了避免维护两套相互矛盾的规则，可以采用下面的方式：

1. 把事实放到共享文档

共享文档 内容

2. 让入口文件只负责导航

CLAUDE.md 和 AGENTS.md 都引用相同的 docs/ 文档，同时只保留各自工具需要的少量使用规则。

3. 将重复流程沉淀为 Skills

例如：

  • frontend-design；
  • backend-development；
  • database-design；
  • testing；
  • code-review；
  • agent-evaluation。

如果需要同时支持两种 Skill 目录，可以维护一套共享源文件，再通过构建、同步或链接方式生成对应目录，但不要让两份内容长期手工漂移。

4. 让测试成为统一验收标准

无论使用 Claude Code 还是 Codex，都应该执行相同的项目验证：

  • 前端：lint + typecheck + unit test + E2E；
  • 后端：lint + typecheck + pytest；
  • 项目：build + security check + Git Diff review。

工具可以不同，但“完成”的定义必须一致。

完成任务必须有证据：

  • 测试结果；
  • 构建结果；

  • 日志和指标；
  • Git Diff；
  • 代码 Review。

不能只因为 Agent 回复“已经完成”，就认为任务真正结束。

5. 让人负责目标和边界，让 Agent 负责执行

在 Harness Engineering 的工作方式中，人和 Agent 的职责逐渐变成：

这不是把软件工程完全交给 Agent，而是把 Agent 放进一个可控制、可验证、可恢复的工程环境中。

九、总结

Claude Code 和 Codex 的意义，不只是让模型能够生成更多代码，而是把模型放进一个真实的软件工程执行环境。

这个环境中包含：

  • Context 与 Rules；
  • Skills、Tools 与 MCP；
  • Permissions、Sandbox 与 Hooks；
  • Subagents 与任务状态；
  • Git、Tests 与 Feedback。

Agent Loop 负责持续运行：

Plan → Act → Observe → Reflect → Repeat

Agent Harness 负责让这个循环能够安全、稳定地发生：

  • 知道项目是什么；
  • 知道应该遵守什么规则；
  • 拥有完成任务需要的工具；
  • 只能在允许的边界中行动；
  • 可以读取真实执行结果；
  • 能够根据失败继续修复；
  • 最终通过测试和审查证明完成。
