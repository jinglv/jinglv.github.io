Agent基础：结构化输出与工具调用

发表于 2026-09-21 分类于 人工智能学习
区分 JSON Mode、原生结构化输出和业务校验，完成一个有边界的工具调用闭环，并明确模型建议与执行权限的分工。

本文是 LLM API 基础系列第三篇。上一篇：生成参数、Token 与上下文管理；下一篇：错误处理与模型适配器。

接口行为核对于 2026-09-21。Python 示例沿用第一篇依赖，Pydantic 使用 v2。

1. 两类契约，不要混为一谈

  • 结构化回答：模型按指定结构输出结果，供界面或程序消费。例如输出一个修改计划。
  • 工具调用：模型提出执行某个函数的请求，应用校验、执行并回传结果。

二者都可能使用 JSON Schema，但“输出一个 action=edit 的 JSON”并不等于文件已被修改；“返回函数名和参数”也不等于调用被授权。[1]

2. 从合法 JSON 到允许执行，中间还有什么

graph TD
    A[模型响应] --> B{完整且未拒答}
    B -->|否| X[停止或修复请求]
    B -->|是| C[解析 JSON]
    C --> D[校验字段和类型]
    D --> E[校验跨字段业务规则]
    E --> F{权限与资源范围允许}
    F -->|否| X
    F -->|是| G[执行或等待人工确认]

图中任意解析或校验失败都应进入停止/修复分支，不能继续执行。对于写文件、发消息、付款等有副作用的工具，还要考虑幂等、审计和人工确认。

2.1 三种机制的边界

机制 主要保证什么 不保证什么
JSON Mode 正常完成时输出可解析的 JSON 字段一定符合你的 schema、业务一定正确
原生 Structured Outputs 在支持的模型和 schema 范围内约束输出结构 事实正确、权限正确，或永远不拒答/不中断
本地校验与执行授权 应用定义的类型、业务及权限约束 自动证明所有外部事实真实

JSON Mode 和原生 Structured Outputs 通常是生成侧的两种选择，不是必须依次开启的两层。无论选择哪一种，都需要应用侧校验。[2]

注意：

  • JSON Mode 通常要求提示中明确请求 JSON；仍要处理空内容、截断和异常情况。[3]
  • Structured Outputs 只支持 JSON Schema 的一个子集，是否支持某种约束要查对应模型文档。
  • “Pydantic 能校验”不代表“生成的完整 schema 一定被服务端接受”。
  • 不支持的 schema 可能直接导致请求报错；拒答可以通过专门字段返回；不能概括成“任何不匹配都会自动重试”。[2]

3. 文件路径校验：不能只检查 startswith(“../“)

原文的检查会漏掉 a/../../secret、绝对路径和指向工作区外的符号链接。下面只演示：在受控、本地、可信工作区中，校验一个已存在的可编辑文件。

allowed_files 必须由应用事先构造为规范化的绝对路径集合，不能直接采用模型输出。Path.resolve() 会解析符号链接和 ..，但这仍然不是完整的文件沙箱。[6]

校验与实际打开文件之间存在竞态（TOCTOU）；恶意进程还可能替换符号链接，硬链接等情况也需要操作系统权限边界。生产工具应在受限进程/容器中执行，并按平台选用安全的文件打开策略。不要让入门示例冒充完整安全方案。

模型输出的 risk="low" 也不是可靠的权限判断。风险、工作区范围、允许动作及审批条件最终由应用策略控制。

4. 自定义工具调用的完整闭环

%%{init: {"sequence": {"width": 100, "actorMargin": 35}}}%%
sequenceDiagram
    participant A as 应用
    participant M as 模型服务
    participant T as 本地工具
    A->>M: 任务与工具定义
    M-->>A: 工具请求与调用 ID
    Note over A: 校验与授权
    A->>T: 执行授权函数
    T-->>A: 返回执行结果
    A->>M: 回传配对结果
    M-->>A: 回答或新工具请求

工具定义只是告诉模型“可以请求什么”。执行始终发生在应用这一侧。 OpenAI 的托管工具是另一种执行边界，不能和应用自定义函数混为一谈。[1]

4.2 改成 Responses 时，改变的是协议映射

步骤 Chat Completions Responses
提出工具请求 message.tool_calls[] output[] 中的 function_call
函数名和参数 call.function.name / arguments item.name / arguments
关联键 tool_call.id function_call.call_id，不是输出项的 id
回传结果 role: tool + tool_call_id type: function_call_output + call_id + output

应用仍然要做同样的授权与执行。OpenAI 手动维护 Responses 上下文时，应按文档保留相关输出项，包括需要回传的推理项；DeepSeek 的状态管理边界另见第一篇。[1][5]

4.3 三条必须保留的边界

  1. 模型只能请求允许的工具：不要 eval 模型返回的字符串，也不要把任意函数名映射到全局函数。
  2. 模型给出的参数必须校验：schema 合法之外，还要检查用户权限和业务资源范围。
  3. 工具结果仍是不可信数据：网页、日志或文件中出现“忽略规则”不能让应用提高它的指令优先级。

工具失败时，可以回传结构化错误让模型调整请求；但要限制循环和修复次数。生产环境还需要独立的工具超时、总任务时限和副作用去重，不能只限制模型调用次数。

5. 本篇小结

能解析，不等于正确；结构正确，不等于安全；模型提出，不等于应用授权。
